# 外部碼離線歸檔修復計畫

> 日期：2026-10-25。依據同目錄的[分析報告](外部碼離線歸檔分析報告.md)（資料基準 2026-10-24）。
> 狀態：計畫已完成、程式碼尚未動工。兩個顯示語意的決定已於 2026-10-25 用可操作原型拍板：列表採**方案 C 殘影內嵌**、橫幅文案按來源分支（原型在 `src/prototype/dead-coupon-proto.tsx`，實作時整檔刪除）。
> 慣例提醒：動工前會先給完整 diff 過目，確認後才進 git。

## 一句話總覽

讓 [ingest_external.py](../../script/site/ingest_external.py) 在每日入庫時順手依 [scan_state.json](../../data/scan_state.json) 把判死的外部碼標成 `offline`。資料層的 60 天清除、復活翻回沿用既有機制；顯示層採方案 C——死檔以殘影卡留在列表（細節見下面「前端怎麼改」）。

改動集中在五個地方：ingest 加一段離線標記走訪、前端列表改為殘影卡內嵌、橫幅文案按來源分支、新增後端單元測試加前端測試調整、三份權威文件同步。sitemap 維持只收 active，不跟著列表走。

## 核心規則

走訪的對象是 coupons.js 裡所有 `source=="verified-external"` 的條目，拿它的 code 去 scan_state 查狀態，判斷只有三條：

1. 狀態是 `dead` 或 `empty` → 標 `offline`，`offlineSince` 取 `dead_since`。**展示上 dead 與 empty 不做區分**（2026-10-25 拍板）：兩者的差異只是掃號池的內部設計預留——dead 是七天觀察窗、empty 是觀察結束後的退役歸檔——對網站而言都是「掃號已判死」。缺 `dead_since` 的遺留形狀（09-04 那 15 筆）退而取券自己的 `lastSeen`，再沒有就用今天。
2. 狀態是 `alive` → 走既有迴圈照常刷新 active。
3. scan_state 查無紀錄 → 不動（無證據不判死；今日 0 筆）。

觀察期內死而復活的碼，網站會如實波動：判死隔天變殘影、復活隔天翻回 active（既有復活路徑自動處理，屬自癒）。「展示反映掃號最新判定」的代價就是這個波動，已確認可接受。

兩個不變的設計約束，來自分析報告的邊界發現：

- 規則只看 `status`，絕不看 `dead_since` 欄位存在與否——[merge_alive_records](../../script/scan/coverage_sync.py#L47-L52) 復活時不清殘留的 `dead_since`，看欄位的規則會誤殺復活碼。
- 判斷完全不用 `state.lastSeen`。它只在入庫時更新，confirm 每日確認活碼並不刷新它，拿它推死亡時點會差好幾十天（26910 差了 25 天）。

冪等性：`offlineSince` 回填的是判死當天（`dead_since`，即偵測當天），每天重跑算出同樣的值，不會漂移。這也讓 60 天清除的起算日是判死那天，不是修復上線那天。

另外：[docs/todo.md](../../docs/todo.md) `6a7ec13` 條目 2 修法方向中「`dead` 走 7 天寬限期」一行已被本決定取代，實作更新 todo 條目時一併修正。

## ingest_external 怎麼改

現在 [main()](../../script/site/ingest_external.py#L122-L170) 的流程是「載入 → 挑活碼 → 沒有就早退 → 逐碼入庫 → 寫檔」。改動是：

- 新增一個小函式，例如 `_mark_offline_by_state(coupons, state_codes, today)`，把上面的三條規則套一遍，回傳翻了幾筆。
- 呼叫點放在挑活碼**之前**。這不是隨意的排序：現在 L136-L138 有個早退（沒有活的外部碼就 `return 0` 不寫檔），離線走訪放在早退之前，才能保證「活碼清零、只剩死碼要歸檔」的那天功能照常運作。
- 寫檔改為無條件執行（本來只在有活碼時寫）。反正同一條 update 鏈後面的 enrich 每天也會重寫 coupons.js，這裡統一行為比較單純。
- 既有的一切照舊：同碼官網優先的 SKIP、9 前綴防呆、[L154-L158 的復活翻回](../../script/site/ingest_external.py#L154-L158)（offline → active 並清 `offlineSince`）、最後 [coupons.js 與 coupons_full.js 一起寫](../../script/site/ingest_external.py#L166-L167)。

走訪只碰 `source=="verified-external"` 的條目。官網碼的離線是 [build_coupons 的 merge](../../script/site/build_coupons.py#L129-L142) 依官網列表管轄的，兩邊職責不重疊，這次也不去動 merge——它對外部碼「原樣保留、交給 ingest」的設計在修復後剛好是對的。

## 前端怎麼改

顯示語意已用原型拍板：**方案 C 殘影內嵌**。死檔不從列表消失，而是以灰化殘影卡留在原列表、排在所有活碼之後，卡面帶「已失效 · 自 X」角標、不提供訂購鈕；搜尋與篩選照常套用。注意這同時改變官網下架券的現行為——它們目前完全隱形，之後也會以殘影卡現身（原型裡 29 筆官網死碼正是這個樣子）。

對應的改動：

- [filter.ts 的 filterCoupons()](../../src/lib/filter.ts#L60)：拿掉「非 active 一律排除」，離線券改為參與搜尋與全部篩選條件。
- [filter.ts 的 sortCoupons()](../../src/lib/filter.ts#L80-L105)：排序鍵最前面加「活碼恆在死碼之前」，其餘規則不變。
- [CouponCard.tsx](../../src/components/CouponCard.tsx#L60)：離線券渲染為殘影形態——灰化降透明、右上角「已失效 · 自 offlineSince」角標、隱藏「前往訂購」連結（代碼複製保留）。
- [CouponDetail.tsx L131-L138](../../src/components/CouponDetail.tsx#L131-L138)：橫幅按來源分支。官網碼維持「已從官網下架（官網已無此優惠，於 X 標記）」；外部碼顯示「掃號已確認失效（自 X 起，官網驗證端點已無此碼）」——兩句都在原型裡實際看過。
- sitemap 不動：[gen_sitemap.py](../../script/site/gen_sitemap.py#L32) 維持只收 active，死碼不進搜尋引擎，但站內使用者看得到殘影。

統計拆分標示：全站數與標籤仍只算 active；列表計數行拆為「共 N 筆 + M 筆近期失效｜全站 X 筆有效」（M 為 0 時省略失效段、失效段灰色），不讓使用者自己做加減法。

## 上線後預期看到什麼

以 2026-10-24 的資料推演，修復隨每日 CI 自動生效，不需要手動跑任何東西：

- 第一次 update 跑完：38 筆翻成 offline，全站 active 從 694 降到 656（10-24 基準，此後每日隨 CI 演進）。這 38 筆全部是 `empty`、全部有 `dead_since`，模擬結果零誤離線。
- 列表不會變短：38 張外部死檔以殘影卡現身、排在活碼之後；連同既有 29 張官網死碼，殘影共約 67 張，隨 60 天清除逐漸遞減。
- 隔天的 sitemap 自動少掉 38 筆死碼深連結。
- 60 天清除日：31 筆在 2026-11-29，其餘 7 筆散在 12-09、12-10、12-13。到那天 merge 自然把它們從 coupons.js 刪掉，之後若復活就以新條目重入。
- 復活情境照舊：explore 盯到活碼 → state 翻 alive → 隔天 ingest 把 offline 條目翻回 active。

驗證方式三件事：重跑 [probe_fix_sim.py](probe_fix_sim.py) 確認 stale 歸零；用 [check_deployed_filter.mjs](../check_deployed_filter.mjs) 對線上站驗證；看當天 daily update commit 的 diff 是否就是 38 筆 status 翻轉。

## 風險與退路

- 誤離線風險：模擬為零，且規則只碰外部碼。就算哪天真的誤標，復活機制每天對著 state=alive 的碼重寫條目，誤標會在隔天自動痊癒，屬於自癒型風險。
- 最壞情況的退路：整個修復是單一 commit，revert 之後隔天 CI 就把 coupons.js 重建回舊行為，沒有不可逆的資料變動（scan_state 從頭到尾沒被寫過）。
