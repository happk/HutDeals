## 前言

### 熔斷是什麼、本專案約定它該長什麼樣

官網在請求過多時回 HTTP 429 或 403，意思是「請求太多，先停」。本專案稱之為**熔斷**，約定的標準處理：

> 收到 403/429 → 停止後續請求 → **已拿到的結果照樣存檔** → 以 exit 3 結束（區別於一般錯誤的 exit 1）→
> CI 的 commit 步驟（PR #8 的 `!cancelled()` 條件）把存檔撿走提交 → 開告警 issue。

這條路在查活階段（`probe_batch`）與官券補全階段（`enrich_official.py`）已實作；
抓詳情階段（`step2_of`）從 docstring 寫「由上層處理」那天起就沒人接——這是整個修復要接回的斷線。

### 要修的缺陷（v1 分析＋兩輪驗收的累積結論）

**BUG ① 熔斷被誤判為 session 過期**（`orderflow.py:246-248`）：
共用 session 管理器的 `except Exception` 不分例外種類，把 403/429 也拿去重配 session，
重配流程再被擋、第二個 403 裸拋。實證：11-12 兩場 traceback 逐幀一致。

**BUG ② 抓詳情迴圈無人接住熔斷**（`daily.py:194/242/324/366` 四處裸呼叫）：
例外炸穿 `main()` → exit 1 → `save_state` 沒跑 → 627 碼成果蒸發。實證：兩場 commit `no changes`。

**BUG ③ gate 查詢吞錯**（`scan.yml:31-53`）：
gate job 無 checkout、`gh issue list` 沒帶 `--repo`，報錯被 `2>/dev/null || echo 0` 吞成 0——
**查詢失敗＝誤判「沒有 issue」＝放行**。實證：#9/#10 開著仍 `gate 通過`；本機 %TEMP% 重現。

**缺口（v2 五缺口＋v2 自身的死代碼）**：
第一輪驗收五缺口（200＋錯誤頁限流、coverage 不入 confirm commit、反向測試順序、gate 空字串、測試涵蓋度）
由校驗證實並全數納入 v2；第二輪複審進一步發現 **v2 的修改③（上層呼叫端與 enrich 加 `except RuntimeError`）是死代碼**——
`RuntimeError` 在上游兩層就被吞成 `None`，上層呼叫端只會收到 `None`，收不到例外。經校驗 v2 以 probe 證實。

### v3 的核心變化：修改③ 改為三層

死代碼的根因是「修法位置沒做落點貫通性檢查」。沿呼叫鏈逐層追（`prepare` 丟 RuntimeError →
`fetch_menu`/`fetch_menu_single` 不攔 → `BatchFetcher.fetch` 攔不到 → `fetch_and_parse` **第一層吞噬** →
`step2_of` **第二層吞噬** → 上層呼叫端只收到 None）之後，最低完整修法是：

| 層 | 位置 | 動作 | 少了它的後果 |
|---|---|---|---|
| 第一層 | `orderflow.py:210-215`（`fetch_and_parse` 通用 except） | 判三關鍵字（`step_1_update`／`users_session_id`／`llcs`）→ 是就 `raise`（**不重試不退避**） | 例外在此被吞、重試三次，下游收 `None` |
| 第二層 | `daily.py:95-99`（`step2_of` 的 `except Exception`） | 同樣判三關鍵字 → `raise`（**不記 step2_error**） | 例外在此被吞，上層呼叫端收 `None` |
| 第三層 | `daily.py` 四處抓詳情迴圈＋`enrich_official.py:72-79` | 接住 `RuntimeError` → `blown=True` → break/中止 | 例外穿出 `main()`，exit 1 而非 exit 3 |

「不重試」「不記 step2_error」是必要的語意調整，不只是放行：第一層若放行但仍重試，會多燒兩倍請求；
第二層若放行但仍記 step2_error，熔斷會污染一般失敗的告警語意。

讓**真實的 `step2_of` 流過**，測試才有能力證偽「例外有沒有穿到 上層呼叫端」。三個案例：

### 修前修後行為對照（v3 完整版）

| 情境 | 現在 | v3 修後 |

| 抓詳情 200＋錯誤頁 | 每碼重試 3 次（掃號端 1875-5625 發） | 第一層即停（每碼 1-3 發）→ 入庫 exit 3 |

| session 過期（真・非熔斷） | 重配一次（正確） | 不變 |
| 非熔斷 RuntimeError（真 bug） | 重試 3 次 → step2_error → 續跑 | 不變（關鍵字不命中） |
| 熔斷日次日 cron | gate 誤放行、再燒配額 | gate 查不到＝擋、三工 skip |
| 熔斷日 coverage 更新 | confirm 不提交、平時也天天丟 | confirm commit 提交（每天不再丟） |
| 手動取消 run | 不撿半成品 | 不變 |

## 研究方法

以唯讀方式分四步定案：

1. **行為對照法**：以 CI log traceback 逐幀還原缺陷鏈，以同晚官券補全端（#9）的正確熔斷為對照組——修復目標是「專案自己已做到的正確行為」
2. **注入驗證法**：mock 注入四種例外建立行為基線——驗收標準動手前凍結
3. **最小修改原則**：每落點 ≤8 行、可單獨回滾；不碰與熔斷語意無關的代碼
4. **落點貫通性檢查**（v3 新增，來自兩輪驗收的教訓）：對每個修改點，從例外產生位置沿呼叫鏈逐層追、
   確認例外真的能穿過中間每一個 `except` 到達落點——**v2 的死代碼正是缺了這一步**
5. **測試證偽力檢查**（v3 新增）：測試的 mock 層級不得移除被測邏輯——mock 對象比照 repo 既有測試（`test_confirm_revive.py`）

工具與腳本：[`test_fuse_after_fix.py`](../test_fuse_after_fix.py)（修改①基線）、[`probe_20261114_verify_v2review.py`](../probe_20261114_verify_v2review.py)（三層驗證探針）。
