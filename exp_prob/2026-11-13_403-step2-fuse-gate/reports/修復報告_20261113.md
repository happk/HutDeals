## 前言

### 熔斷是什麼、本專案約定它該長什麼樣

官網會在請求過多時回 HTTP 429 或 403，意思是「你請求太多了，先停」。
本專案把這個信號稱為**熔斷**，約定的標準處理是：

> 收到 403/429 → 停止後續請求 → **已拿到的結果照樣存檔** → 以 exit 3 結束（區別於一般錯誤的 exit 1）→
> CI 的 commit 步驟（PR #8 加的 `!cancelled()` 條件）把存檔撿走提交 → 開告警 issue。

這條路已經在「查活」階段實作（`daily.py` 的 `probe_batch`），也在官券補全階段實作（`enrich_official.py`）——
11-12 晚間官券補全撞上 403 時就是這樣走完的：26 張已補全的資料入庫、開出 issue #9，一切按設計。
**問題在第三個使用者——「抓詳情」階段——從頭到尾沒實作這條路。**

### 要修的三條 BUG 詳述

行號以 origin/main `26bbdda` 為準；完整 CI log 證據鏈見查找報告，本節為修復視角的重述。

**BUG ①：403 被誤當成「session 過期」**（`script/lib/orderflow.py:246-248`）

抓詳情階段多張券共用一個訂餐 session，`BatchFetcher` 負責管理它。現行代碼：

```python
try:
    html = self._session.fetch_menu(code)
except Exception:
    # session 過期/其他錯誤 → 重配一次；若仍錯往上拋（含 429/403 熔斷）
    self._roll(code)
    html = self._session.fetch_menu(code)
```

`except Exception` 不挑食：session 過期和官網 403 被一視同仁，全部去重配新 session。
但限流狀態下，重配流程（配 cookie、取門市參數、選門市的 `step_1_update`）**自己也會被擋**——
於是冒出第二個 403。這個 403 從重配流程直接往上炸，此時最初的 except 已經用掉了，
外面沒有任何人接它（下一條 BUG 就是它沒人接的原因）。
註解裡寫的「含 429/403 熔斷」只是把問題記在紙上，代碼並沒有區分。

**BUG ②：抓詳情迴圈沒人接住熔斷**（`script/scan/daily.py` 四處）

`step2_of` 的文件（daily.py:86）寫「429/403 原樣往上拋由上層呼叫端處理」，
但上層從未實作：confirm 的活券迴圈（daily.py:194）、confirm 的復活補抓（daily.py:242）、
explore 的補抓（daily.py:324）、sample 的補抓（daily.py:366）——四處全是裸呼叫，沒有 try。
於是 BUG ① 冒出的裸例外一路炸穿到 `main()`，程式以 **exit 1**（一般錯誤）結束，
而不是熔斷約定的 **exit 3**。

真正的損害在這裡：`save_state`（把 627 碼查活結果寫入 `data/scan_state.json`）、
`update_alerts`、`history_row` 全部排在迴圈之後——程式死在它們之前，
**46 分鐘掃完的 627 碼結果一行都沒落地**。
11-12 兩場 CI 的 commit 步驟都只看到 `no changes`，什麼也沒撿到。

**BUG ③：熔斷日保險形同虛設**（`.github/workflows/scan.yml:35-40`）

`scan.yml` 的第一個 job（gate）是保險：查有沒有未關閉的失敗告警 issue，有就禁止今日掃號（防污染）。
但它有兩個洞：

1. gate job 沒有 checkout 程式碼，`gh issue list` 也沒帶 `--repo`——
   gh 在非 git 目錄會報 `fatal: not a git repository`（本機在 %TEMP% 重現確認）。
2. 指令寫成 `gh issue list … 2>/dev/null || echo 0`——gh 失敗被吞成 0，**「查詢失敗」被當成「沒有 issue」**。

兩洞合起來：熔斷日隔天，gate 根本查不到 issue，照樣放行。
實證：11-12 22:40 的備援場起跑時 #9/#10 都還開著，gate 卻輸出「gate 通過，可掃號」——
又燒了一輪 627 發、又撞了一次 403。

### 三條的因果關係

- BUG ①＋② 是**同一事故的兩個環節**：① 把熔斷變成無人處理的裸例外，② 確保沒人處理它。
  只修①，403 還是會炸（炸點後移）；只修②，403 可被接住但重配仍在白燒請求。兩處都要修。
- BUG ③ 是獨立的保險失效：不參與本日損害，但讓熔斷日無法止損（22:40 的二次燒配額就是被它放行的）。

### 修復範圍邊界

| 修 | 不修 | 理由 |
|---|---|---|
| BUG ①②③（上述三條） | 11-11 dispatch-update 卡 queued | runner 配額耗盡的一次性事件，備援 cron 已兜住 |
| 同上 | session 管理架構重構 | 重配機制自 2026-09-08 上線從未誤傷非熔斷錯誤，無需大改 |
| 同上 | 「抓詳情失敗改回報 None」的替代方案 | 會把熔斷混進一般失敗的告警欄位（污染語意），且停止前仍繼續燒請求 |

### 修復後的目標行為

一句話：**抓詳情撞熔斷 ≡ 查活撞熔斷**——撞到 403 就停手、已完成的成果照樣入庫、exit 3、issue 照開。
修復不發明新機制，只是把「文件上寫了、代碼裡沒有」的那條既有約定接回去。

## 研究方法

以唯讀方式分三步定案：

1. **行為對照法**：以 CI log 的 traceback 逐幀還原缺陷鏈，再以同晚官券補全端（issue #9）的正確熔斷處理為對照組——
   修復目標不是「理想中的行為」，是「專案自己已經在別處做到的正確行為」。
2. **注入驗證法**：403 無法從外部可靠觸發（不能命令官網限流），改以 mock 注入四種例外
   （403／429／500／連線超時）對現行代碼建立行為基線——**驗收標準在動手之前先凍結**。
   實測結果：403/429 確實觸發重配（缺陷重現），500/超時走正常重配（無既有問題）。
3. **最小修改原則**：三處修改各自獨立、每處 ≤10 行、每處有單獨的回滾判準；
   不碰任何與熔斷語意無關的代碼。歷史教訓（9f44bb9-1「條件寬一點」的修法曾造成二次事故）支持收窄。

工具與腳本：[`test_fuse_after_fix.py`](../test_fuse_after_fix.py)（注入測試，零真實請求）。
