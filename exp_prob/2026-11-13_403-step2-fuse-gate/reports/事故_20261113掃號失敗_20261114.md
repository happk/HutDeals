- **不是卡在同一個號段。** 三場的第一個 step2 目標都是 `15809`，那是 `sorted()` 排序的必然結果
  （`15596` 永遠排第一、但每場查活都判 dead），與號碼本身無關。

### step2 階段的速率量測——403 的真正觸發面

這一節回答「為什麼偏偏是 step2 階段吃 403」，是本波事故裡唯一能與官網限流機制對上的量化證據。

**量測方法**：取 11-10 的完整成功場（run [42862287590](https://github.com/happk/HutDeals/actions/runs/42862287590)）的 log，
以 M1 首筆到末筆、M1 末筆到 `confirm 完成` 兩段時間差，換算兩個階段的請求密度。
選 11-10 是因為它是最近一場「M1 + step2 全程跑完且無任何 step2 錯誤」的 run。

| 階段 | 耗時 | 請求數 | 密度 |
|---|---|---|---|
| M1 查活 | 45.5 分（2731 秒） | 627 發 | **0.23 發/秒** |
| step2 抓詳情 | 5.3 分（316 秒） | 約 661 發（625 碼 + 12×3 換 session 前置） | **1.98 發/秒** |

**密度差 8.6 倍。**

**這個差異的原因是節流只做了一半。** [`probe_batch`](../../../script/scan/daily.py#L53) 的迴圈尾端有
[`sleep_scan(i, codes)`](../../../script/scan/daily.py#L76)——2 秒基礎 + 0~2 秒抖動、每 50 發 30 秒長休、換號段再追加。
但 `cmd_confirm` 的 alive 抓詳情迴圈（[`daily.py:178-232`](../../../script/scan/daily.py#L178)）**一次 sleep 都沒有**：

```
alive 迴圈內 sleep_scan 呼叫次數: 0
alive 迴圈內 step2_of 呼叫:    1
```

於是 step2 階段變成「以 M1 的 8.6 倍密度連續打 5 分鐘」。

**這解釋了成功與失敗的分野。** 11-10 與 11-11 之所以成功，不是因為官網好心——
是因為 step2 階段只花 5.3 分鐘就打完了，總量還沒累積到觸發閾值。
11-12 與 11-13 的 M1 階段同樣累積了 627 發（差別只是多了幾次重試、多了幾秒），
進 step2 時又以 2.0 發/秒 的密度打，第一發就撞上已經逼近上限的配額。

**三場失敗的時點也一致**：都在「M1 跑完後第 46-47 分鐘」。這個一致性比較像**滾動窗口的累積量**觸發，
而不是瞬時速率——也就是說，進入 step2 時配額已經所剩無幾，密度只是壓垮它的最後一根稻草。

**順帶回答「是不是卡在同一個號段」**：三場的第一個 step2 目標都是 `15809`，
但那是 [`sorted()` 排序](../../../script/scan/daily.py#L160) 的必然結果——
`15596` 永遠排第一，而它每場查活都判 dead（跳過 step2），所以永遠輪到 `15809`。
換個起點也一樣會在第一發撞牆，因為限流是「你已經打了 627 發」造成的，與號碼無關。


三場的擋點略有不同（第二次限流比第一次更早生效），但形態完全同型。

## 討論

### 這不是新 bug

本次 traceback 與 11-12 兩場**逐幀一致**，包括行號。這代表：

1. 主代碼在這三天**沒有被改動過一行**（`headSha` 都是 `26bbdda`）。
2. 修復計畫（v1→v4）全部停留在文件層，沒有一處落地。
3. 同一個缺陷會**每天復發**，每次帶走當天全部查活成果。

這三天的實際產出是：6 份計畫（v1／v2／v3／v4＋修復方法＋README 更新）、
3 份校驗、4 份驗收（含本報告）、5 個 commit。**主代碼 diff 為零。**

### 為什麼「先把計畫做對」的代價比想像中高

前三輪的迭代都有實質價值：v2 發現死代碼、v3 修正測試層級、v4 發現垃圾成功形態。
每一輪都讓計畫更接近正確。

但代價是：**每延一天，就多損失一天的 627 碼掃號成果**。而這條 bug 的修復其實早在 v1
就已經有可用的最小版本（`orderflow.py` 三行 + `daily.py` 四處 try）。

這不是說前三輪白做——v4 的 ⑥ 確實抓到了更嚴重的形態。而是說：
**修復的價值是「停止每日損失」，計畫的價值是「一次修對」。當兩者衝突時，
應該考慮先落地已知正確的部分（①、②、③、④、⑤），把新發現的部分（⑥）留給下一輪。**

具體來說，v1 的三處修改（`orderflow.py:246-248`、`daily.py` 四處、`scan.yml:31-53`）
在 v2／v3／v4 三輪裡從未被推翻過——它們一直是對的。若 11-13 就先落地這三處，
今天這場的 627 碼就會保住（走 exit 3 + 入庫），而不是蒸發。

### gate 與 alert 的兩個次生問題

**gate 仍 fail-open**：`#9`／`#10` 都 open，但 gate 輸出「gate 通過」。
這是因為 gate job 沒有 checkout、`gh issue list` 沒帶 `--repo`、錯誤被 `|| echo 0` 吞掉。
這個缺陷從 11-12 22:40 場就存在，本次照樣復發。

**alert 把連續失敗吞掉了**：alert job 的邏輯是「若已有 open 的 `scan-failed` issue 就 skip」。
結果是 `#10` 從 11-12 開到現在，11-12 22:40 與 11-13 17:11 兩場失敗都只在 log 裡留一句
`open scan-failed issue already exists, skip`——**沒有 comment、沒有新 issue、沒有任何通知**。

這意味著：如果沒有人主動去看 Actions，第二次、第三次失敗是完全靜默的。
`#10` 的 body 指向的是 11-12 17:11 那場的 run URL，看 issue 的人不會知道後面還有兩場。

**建議**（不在本報告執行範圍）：
- gate 修法同 修改⑤（`GH_REPO` ＋ 去吞錯 ＋ 整數驗證）
- alert 的 skip 分支改成「**在既有 issue 補 comment**」，附上新 run 的 URL 與失敗摘要。
  這只需要在 `else` 分支加一行 `gh issue comment`，比開新 issue 更不打擾。

<a id="avoid-403"></a>
### 如何規避 step2 的 403

前三節講的是「被擋之後為什麼會損失」。這一節回答另一個問題：**能不能不被擋。**

先排除兩個常見猜測，兩者都不成立：

**不是 cookie 的問題。** 崩潰發生在 `BatchFetcher` 全新建的 session 的第一發請求上。
[`BatchFetcher.fetch:242-243`](../../../script/lib/orderflow.py#L242) 的 `_session is None` 分支觸發 `_roll()`，
走完 `prepare()` 的完整前置（配 cookie、取 `users_session_id`／`llcs`／`llcstmsp`、選門市），
才發出第一個 `fetch_menu`。也就是說被擋的那一發，用的是**全新且剛驗證過可用的 session**。

更重要的是：換 cookie 在這裡是**損害放大器**而非解方。第一個 403 本來只是「這一發被擋」，
是 `BatchFetcher` 的 `except Exception` 決定去換 session，才讓重配流程（又多燒 3-4 發）再吃一次 403 並炸穿進程。
把「換 cookie」當解法，等於在錯誤的方向上加碼。

**不是「等不夠久」。** 兩個層面都不成立：

- 時間上：最後一筆 M1 在 `17:58:43`，traceback 在 `17:58:46`——間隔 **3 秒**。
- 機制上：抓詳情迴圈根本沒有等待機制。`cmd_confirm` 的 alive 迴圈（[`daily.py:178-232`](../../../script/scan/daily.py#L178)）
  裡 **`sleep_scan` 呼叫次數為 0**，而查活迴圈有。

**真正的原因是速率不對稱**，量測見[結果的速率量測一節](#step2-rate)：
M1 以 0.23 發/秒 打 45.5 分鐘，step2 以 1.98 發/秒 打 5.3 分鐘，密度差 8.6 倍。
節流只做在查活階段，抓詳情階段完全裸奔。

#### 三個可規避的做法

**做法一：給 step2 迴圈補上與 M1 同級的節流**

在 [`daily.py:194`](../../../script/scan/daily.py#L194) 的 `d = step2_of(r, fetcher)` 之後加一行
`sleep_scan(i, alive)`（比照 [`probe_batch:76`](../../../script/scan/daily.py#L76) 的用法）。

| 項目 | 現況 | 加節流後（估算） |
|---|---|---|
| 每碼間隔 | 0 秒 | 2~4 秒浮動 |
| step2 階段總時長 | 5.3 分 | 約 25~40 分 |
| 瞬時密度 | 1.98 發/秒 | 約 0.3 發/秒（降 85%） |
| confirm 總時長 | 約 51 分 | 約 75~90 分 |

這是把 step2 的密度壓回與 M1 同一量級，**直接針對量測到的 8.6 倍落差**。
成本是每天多 25-40 分鐘的執行時間（runner 分鐘數仍在免費額度內）。

**做法二：把 `BatchFetcher(k=50)` 調小（如 k=20）**

效果存疑，理由：換 session 更頻繁會讓**單 session 的請求密度分散**，
但每個新 session 要多打 3 發前置，總請求量反而上升：

| k 值 | 總請求數（625 碼） |
|---|---|
| 50 | 625 + 13×3 = 664 |
| 20 | 625 + 32×3 = 721（+8.6%） |

只有在「限流按 session 生命週期計數」時才有效。而三場事故的觸發點都在
「M1 打完後的 step2 第一發」，比較像按 IP 的累積量，所以這條的預期效果低。
**建議不做，或等做法一落地後再觀察是否需要。**

**做法三：把 M1 與 step2 拆成兩個 job，中間隔開**

`confirm` 現在把兩階段串在同一個 job 裡。拆開可以讓官網的累積計數器有時間衰減。

理論依據最強（三場都在 M1 跑完 46-47 分鐘後觸發，強烈暗示滾動窗口），
但工程成本最高：需要新增 job、跨 job 傳遞 state、且**窗口長度未知**——
若窗口是 1 小時，間隔就得設 1 小時以上，confirm 會從 51 分鐘變成近 2 小時。

**建議列為第二階段**：先做做法一，觀察是否還會觸發；若仍會，再考慮拆 job。

|---|---|---|
| 1 | 做法一（step2 加節流） | 改一行、直接對症、可立即驗證 |
| 2 | 修改①～⑤（接住 403） | 節流只能降低機率，接住才能保住成果 |
| 3 | 做法三（拆 job） | 若做法一不足以避免，再上這個 |
| 不建議 | 做法二（調 k） | 請求總量上升，預期效果低 |

#### 一句話總結

**節流降低被擋的機率，接住 403 保住被擋後的成果——兩者解決不同問題，都需要做。**
目前的狀況是：節流只做了一半（M1 有、step2 沒有），而接住則完全沒有做。
這兩件事同時缺失，才有了三場連續的 627 碼蒸發。
