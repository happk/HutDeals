## 摘要

- 速報的**兩個阻斷、四個次要、一個已驗證論證，判定全部成立**——v3 的三層確實堵不住 200＋忙碌頁形態，
  測試層級確實繞過 ③a，dead 迴圈確實會在熔斷後再打 step2。
- 但阻斷一的**機制描述需要修正**：速報說 busy 頁會「`parse_menu_html` 解析失敗回 None → 重試三次 → 1875 發」，
  我以真實解析鏈（真 `parse_step2`／`parse_orderflow`／`flatten_items`＋node）實測——**非空 busy 頁根本不會回 None**，
  它回一個帶垃圾 meta 的 dict，被當成「解析成功」。
- 這個修正讓損害評估反轉：真實形態不是「每碼 3 發＋625 筆 step2_error」，
  而是「**每碼 1 發、零失敗訊號、title/channels/desc 被靜默清空、content_changes 假告警爆量、exit 0**」——
  比速報描述的更糟，因為它連失敗的痕跡都不留。
- 修正同時**反轉了速報補法的落點**：在解析失敗分支做「連續 N 碼解析失敗」計數，
  對垃圾成功形態無效（該形態不進解析失敗分支）。補法應先做「選單版有效性判定」——
  材料現成：[`is_menu_page`](../../../script/lib/orderflow.py#L133)（ctidss＋長度門檻）目前**全 repo 無人呼叫**。
- v4 計畫需要吸收：兩個阻斷照採，阻斷一的補法改寫為「有效性判定＋連續 N 碼計數」的組合。

## 研究方法

以唯讀方式分三步：

1. **真實鏈路探針**（本輪新增的方法）：不 mock 解析層，讓 `fetch_and_parse` 帶著真的 `parse_menu_html`
   （含 node `extract_js.cjs` 子進程）跑三種合成頁面——短忙碌頁、文字版樣式頁、空回應——
   看控制流實際走哪條分支。速報的探針把 `parse_menu_html` mock 成 None，這正好把待驗的前提藏進了實驗設定。
2. **綁定層級探針**：呼叫計數器包住 `orderflow.fetch_and_parse`，驗證 mock `daily.fetch_and_parse` 時 ③a 是否被執行。
3. **文檔逐條核對**：四個次要的行號與內容，以及速報引用的 v3 行號（L96/97/123）逐一對照現檔。

## 討論

### 為什麼「垃圾成功」比「解析失敗重試」更危險

解析失敗形態會留下訊號：log 的 `attempt 1/3` 行、`step2_error` 留痕、alerts 可見——有人看得見。
垃圾成功形態**零訊號**：每碼 1 發就「成功」，run 以 exit 0 收場，
`title`／`channels`／`desc_head`／`desc` 被清空、每張活碼都掛上當天的 `contentChangedAt`、
`content_changes` 告警灌進 625 筆假差異——污染直接入庫、隔天 deploy。
probe 2 對真實 `cmd_confirm` 的實測就是這個結局（單碼版）。

文字版樣式（1b）還暴露第二層風險：它的 meta **看起來完全正常**（title、channels 都對），
只有 `items=None` 可辨——這排除了「title 為空」當垃圾判定條件的做法，
也說明為什麼有效性判定要用結構特徵（ctidss）而非內容特徵。

### 對 v4 補法的具體意涵

速報補法的方向（熔斷判定要能抓「無例外的解析失敗」）是對的，但落點要改兩步：

1. **先讓垃圾成功變成可見的失敗**：把選單版有效性判定放進抓取路徑——
   [`is_menu_page`](../../../script/lib/orderflow.py#L133) 已經寫好了（`len>180_000 且含 ctidss`），目前全 repo 無人呼叫。
   在 `fetch_and_parse`（或 `parse_menu_html` 回傳前）加「非選單版 → 視同解析失敗」，
   垃圾成功形態就會流進現有的解析失敗分支，與空回應形態合流。
2. **再加速報的連續 N 碼計數**：合流之後，「連續 N 碼解析失敗 → 熔斷」的計數器才有東西可數，
   N=3 比照 `FETCH_RETRIES` 的語意也成立。

修改③ 的命名取捨（擴寫定義 vs 新立 修改⑥）維持速報的判斷——留給計畫作者；
本校驗只指出：無論掛在哪個編號下，「有效性判定」是「連續計數」的前置，兩者是依賴關係不是並列關係。

## 未解事項

- 官網是否真的會以 200＋忙碌頁表達限流：與速報、v3 相同的風險推演（兩場事故都是 403）——
  本校驗的合成頁面實驗證明的是「若發生，控制流走哪條」，不依賴 busy 頁的確切內容。
- 真實忙碌頁的形態（短頁／文字版／其他變體）未知：1a 與 1b 的差異顯示不同變體的污染程度不同，
  Phase 6 真熔斷驗收時應記下實際頁面樣貌。
- 有效性判定的門檻（`is_menu_page` 的 180_000＋ctidss）對「正常頁面變體」的誤傷面：
  `MENU_MIN_LEN` 是 2026-09 的實測值，官網改版可能漂移——若 v4 採用，需在未解事項追蹤。
- 掃號端每碼 1 發的數字以共用 session 為前提（前置 3 發由整批分攤）；enrich 4 發＝`prepare` 3 發＋抓取 1 發。
