# 每日掃號 403 之後——一個炸掉的熔斷出口，與 627 碼的蒸發

2026-11-13 · HutDeals（issue #9 / #10）唯讀分析

> 本報告調查 2026-11-12 兩條自動告警（#9 每日爬蟲失敗、#10 每日掃號失敗）。
> 全程唯讀：未修改任何程式碼、未提交、未關閉 issue。

## 摘要

- 背景：11-12 兩場 CI 失敗——update 管線（enrich 官券補全）與 scan 管線（confirm 掃號）都在中途吃官網 HTTP 403。
  兩條 issue 由告警機制自動開出，機制本身運作正常。
- 掃號實況（分兩半）：**查活階段（627 碼逐碼問官網「券還能用嗎」）100% 完成、46 分鐘、官網未擋任何一發**；
  **抓詳情階段（對活券打開詳細內容頁）第一發就被擋、0 張完成**；
  且查活成果因崩潰 0% 入庫——46 分鐘的工作蒸發。
- 方法：下載兩場 run 的 Actions log 逐幀比對（失敗 run 43142259147 / 43266704668 / 43322131238，成功對照組 43119695744）→
  對照 `daily.py` / `orderflow.py` / `enrich_official.py` 的呼叫鏈定位拋出點 → 本機煙霧驗證（查活單發、詳情頁單發、`confirm --limit 5`、中斷點 ±15 區段兩輪）。
- 結論：**觸發是官網限流（403），不是官網改版；但 403 之後的損害有一半是代碼缺陷**。
  update 管線（#9）的熔斷處理完全正確——補全 26 張入庫、exit 3、開 issue，皆按設計；
  scan 管線（#10）則暴露真實 bug：抓詳情階段的 403 被誤判成 session 過期去重配 session，
  重配時的第二個 403 成為無人接手的裸例外，**炸掉整個進程——查活已完成的 627 碼結果全部蒸發**。
  另外，熔斷日應擋住次日掃號的 gate 因 gh 無 repo context 誤判放行（獨立缺陷，已實證一次）。

### 判讀原則

- 429/403 在本專案是「熔斷信號」不是錯誤：設計上有專門出口（`blown=True` → 部分結果入庫 → exit 3 → CI commit step 撿走）。
  判斷代碼是否有問題，看的是「熔斷信號有沒有走完這條路」，不是「有沒有 403」。
- CI log 的 traceback 是逐行證據；呼叫鏈以 traceback 的檔案行號反推，不猜。
- 官網行為是黑盒：本分析只做小批量煙霧實證（合計 < 200 發，間隔 ≥1s），不做壓力測試。

## 研究方法

以唯讀方式分四步進行：

1. 讀兩條 issue 的 body 與對應 run 的 job/step 結論，圈定失敗 step
2. 抓 `--log-failed` 完整 traceback，以行號對照 `origin/main` 的原始碼定位拋出鏈
3. 拉近 10 天 run 歷史與 11-11~11-12 全部 run 的時序，排除/確認「持續封鎖」「同型重演」「排程備援」三種假說
4. 本機煙霧實證（四段：單發 M1＋step_2、`confirm --limit 5` 備份還原制、中斷點 15809±15 兩輪一致性、step_2 尾測）

工具與腳本：`probe_20261113_smoke_m1_step2.py`、`probe_20261113_range_15809pm15.py`（本資料夾）。

## 結果

### 兩場 scan 失敗的完整還原（issue #10）

17:11 場（43266704668）與 22:40 場（43322131238）完全同型。

**第一半：查活——完全成功。**
627 碼逐碼問完，46 分鐘，結果 624 張活、2 張死（16311/16312），中途僅 1 碼網路超時重試成功，**官網全程未擋任何一發**。但此刻結果只在記憶體，尚未寫檔。

**第二半：抓詳情——第一發即失敗。**
對活券逐一抓內容頁，第一個目標 15809 就被官網回 403，0 張完成。

**第三件事：成果蒸發。**
程式在抓詳情一開始崩潰，寫檔（`save_state`）永遠沒執行——第一半 46 分鐘的查活成果 0% 入庫，CI 事後 commit 檢查只見 `no changes`。

### BUG 的本質（#10 三層拆解）

1. **觸發層（官網）**：403 是限流。兩場都發生在「查活 627 發完成後的第一個詳情頁 session」；
   11-11 23:25 場（同代碼）三工全成功、11-13 本機煙霧亦通——非持續封鎖、非改版、非 IP 封鎖。
2. **誤判層（共用 session 管理器）**：`orderflow.py:246-248` 的 `except Exception` 把熔斷信號當成「session 過期」，
   重配 session 不但救不回來，重配流程本身又多燒 3-4 發被擋的請求。
3. **缺口層（cmd 層）**：`step2_of` docstring（`daily.py:86`）寫「429/403 由 cmd 層處理」，
   但 `cmd_confirm`/`cmd_explore`/`cmd_sample` 的抓詳情迴圈（daily.py:194、242、324、366）全是裸呼叫——
   **查活端有的熔斷出口（`probe_batch` ABORT → blown → exit 3），抓詳情端從一開始就沒接上**。

## 討論

### 三問的直接回答

1. **「只是網路波動/伺服器問題，而非代碼問題？」**——不成立。觸發是官網限流（伺服器端），但 #10 的損害擴大（627 碼蒸發）是代碼缺陷：熔斷信號在抓詳情路徑被誤判、炸掉進程。#9 則純粹是設計內熔斷，代碼無問題。
2. **「此次只是修 gate？」**——不止。修復範圍有二：抓詳情熔斷語意（根因，A+C 案）＋ gate fail-closed（防污染保險失效）。gate 修的是「限流日別再燒配額」；抓詳情修的是「就算撞了成果也保得住」。兩者都還沒動手。
3. **具體 BUG 案例**——見「結果」第一表：15809 的詳情頁得 403 → 共用 session 管理器的 `except Exception` 誤判為 session 過期 → 重配 session → 重配的 `step_1_update` 再吃 403 → 裸例外炸穿 `main()`。對照組是同晚官券補全端的 `ABORT 91116 → exit 3 → 26 張入庫`。

### 為什麼 gate 沒擋住

- gate job 無 `actions/checkout`，`gh issue list` 未帶 `--repo`：gh 在非 git 目錄報 `fatal: not a git repository`（本機 %TEMP% 重現確認）。
- `2>/dev/null || echo 0` 把 gh 失敗吞成 0——**fail-open**：查詢失敗＝誤判「無 open issue」＝放行。
- 22:40 場 gate log 只有 `gate 通過，可掃號`、無任何 gh 輸出，與此吻合。
- 修法：gate step 加 `GH_REPO: ${{ github.repository }}` env，並移除吞錯改 fail-closed（查不到＝擋）。

### dispatch-update 卡 queued（11-11 場，非本日 bug）

- 三工 success 但第五 job 自 20:29:26 起 `status=queued` 至今，0 steps；run 整體被回填 failure。
- 本質是 runner 併發池耗盡，非腳本問題；alert 因 `needs` 三工 success 而 skip，故未開 issue。
- 備援 cron 已兜住（23:25 場接手），無行動必要。

### 修復方向（僅方向，本分析未執行）

- **A＋C 案**（建議）：共用 session 管理器的 except 先判 `is_rate_limited`——403/429 不重配、原樣上拋（orderflow.py:246-248）；
  cmd 三工迴圈外接 `except HTTPError: if is_rate_limited(e): blown=True; break`（daily.py:194/242/324/366）→ 走既有 `return 3 if blown`。
  修後語意：抓詳情撞熔斷＝查活撞熔斷，**失敗也入庫**（部分結果寫檔）、exit 3、issue 照開。
- 不採 B 案（step2_of 回 None 記 step2_error）：熔斷混入 step2_error 會污染 alerts 語意，且迴圈繼續燒配額。
- 「熔斷後重試」不採：403 是官網叫停的信號，當場重試＝繼續撞牆；補數由次日排程自然完成（confirm 每日重查全部活碼）。
- gate 修法見上。commit 前依規矩申請授權。

## 未解事項

- 官網限流的確切機制：兩場 403 都在「查活 627 發＋詳情頁 session 建立」之後，但門檻是按 IP 每小時、按 session 生命週期、還是按端點組合，無法從外部驗證。
- 22:40 場 gate 放行時 gh 的實際 stderr：CI log 中被 `2>/dev/null` 吞掉，無法逐字確認報錯內容（非 git 目錄 fatal 是本機重現的等價證據）。
- 11-11 dispatch-update 的 runner 飢餓原因：GitHub 控制面不留細節，只能確認狀態（queued 空轉＋run 回填 failure），無法取證。
