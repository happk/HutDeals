### v3 之後多了什麼：第三輪複審＋校驗的兩個層次

第三輪複審（速報）與我方校驗對 v3 的判定一致：**三層架構（修改③）成立、「BatchFetcher.fetch 不需改」成立**，
但 v3 對「200＋錯誤頁」形態的覆蓋只做了一半——速報的兩個阻斷經校驗全部證實：

1. **零例外形態沒堵（阻斷一）**：11-12 的 403 打在 `fetch_menu` 的 GET（[`orderflow.py:124`](../../../script/lib/orderflow.py#L124)）。
   同一位置若改回「200＋忙碌頁」，控制流裡**沒有任何例外**，③a／③b／③c 全部碰不到。
2. **測試層級繞過 ③a（阻斷二）**：[`daily.py:26`](../../../script/scan/daily.py#L26) 是 `from ... import fetch_and_parse`，
   mock `daily.fetch_and_parse` 不會執行 `orderflow.fetch_and_parse`（③a 所在）——③a 無效時 v3 的三案例測試依然全綠。

**校驗對阻斷一的修正（v4 設計的關鍵輸入）**：速報描述的路徑是「`parse_menu_html` 回 None → 解析失敗重試三次」，
但校驗以**真實解析鏈**實測——非空 busy 頁**不會回 None**：`parse_step2` 永不 throw（[`parse_step2.py:194-218`](../../../script/scan/parse_step2.py#L194)）、
node 對無資料頁 exit 0 回全 null JSON、`flatten_items` 空結構回 None——`parse_menu_html` 回一個帶垃圾 meta 的 dict，被當成**解析成功**。
實測結局（[`probe_20261114_verify_v3review.py`](../probe_20261114_verify_v3review.py) P1/P2）：
每碼 **1 發**、零 step2_error、`title`／`channels`／`desc` 被**靜默清空**、`contentChangedAt` 全洗＋`content_changes` 假告警爆量、**exit 0**——
比速報估的「1875 發＋625 筆 step2_error」更糟，因為連失敗的痕跡都不留。速報描述的「解析失敗×3」只在**空回應**子形態成立。
文字版變體的 meta 甚至看起來完全正常（title/channels 都對），只有 `items=None` 可辨——垃圾判定必須用**結構特徵**，不能用內容特徵。

因此 v4 新立**修改⑥**（非選單頁形態的熔斷），與 修改③（RuntimeError 三層）並列：
兩者機制不同（例外路由 vs 資料有效性判定）、落點不同、可各自獨立回滾——這是速報留下的命名取捨，v4 選「另立」而非「擴寫 ③ 的定義」。

### 修改⑥ 的設計（校驗反轉後的補法）

速報的補法（在解析失敗分支做「連續 N 碼解析失敗」計數）對垃圾成功形態**無效**——該形態不進解析失敗分支。
校驗確認正確順序是兩步依賴，v4 照此落地：

| 步 | 位置 | 動作 | 少了它的後果 |
|---|---|---|---|
| ⑥a 有效性判定 | `orderflow.py`：`is_menu_page` 改模組函式；`fetch_and_parse` 解析分支加條件 | 非選單版（無 ctidss 或長度不足）**視同解析失敗**，與空回應合流 | 垃圾成功繼續靜默污染，計數器無東西可數 |
| ⑥b 連續計數熔斷 | `daily.py` 四處迴圈＋`enrich_official.py` | 連續 N 碼解析失敗（N＝3，比照 `FETCH_RETRIES`）→ `blown=True` → break，走既有 exit 3 | 掃號端照掃 625 碼×3 發（1875 發）才自然結束 |

材料現成：`is_menu_page`（ctidss＋`MENU_MIN_LEN`=180_000，[`orderflow.py:133`](../../../script/lib/orderflow.py#L133)）
2026-09-06 就寫好了，findstr 證實**全 repo 無人呼叫**——v4 只是把這道閘門接進抓取路徑。
材料選結構特徵（ctidss）而非內容特徵的理由：文字版變體的 title/channels 都正常（校驗 1b 實測），內容特徵不可靠。

## 研究方法

以唯讀方式分六步定案（1-5 承 v3，6 為本輪新增）：

1. **行為對照法**：以 CI log traceback 逐幀還原缺陷鏈，以同晚官券補全端的正確熔斷為對照組
2. **注入驗證法**：mock 注入建立行為基線——驗收標準動手前凍結
3. **最小修改原則**：每處獨立可回滾；不碰與熔斷語意無關的代碼
4. **落點貫通性檢查**：對每個修改點，從例外產生位置沿呼叫鏈逐層追——v2 死代碼的教訓
5. **測試證偽力檢查**：mock 層級不得移除被測邏輯——v2 假陽性的教訓
6. **真實鏈路探針法**（v4 新增，來自第三輪的教訓）：驗證「某層會怎樣」的前提時，**不得 mock 該層本身**——
   速報把 `parse_menu_html` mock 成 None，正好把待驗的前提藏進了實驗設定；校驗改用真實解析鏈才發現垃圾成功形態。
   本計畫 ⑥a 的測試設計遵守同法：mock 只允許放在被測閘門的**下游回傳值**，閘門條件本身走真實代碼。

工具與腳本：[`test_fuse_after_fix.py`](../test_fuse_after_fix.py)（修改①基線）、
[`probe_20261114_verify_v2review.py`](../probe_20261114_verify_v2review.py)（三層驗證探針）、
