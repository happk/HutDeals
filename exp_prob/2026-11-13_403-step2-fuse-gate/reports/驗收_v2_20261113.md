## 摘要

- v2 相對 v1 有實質進步：五個缺口全部納入、push 移到反向測試之前、邊界表補上「刻意不修」、修改④ 讓 coverage 進入 confirm 的 commit。這些都對。

## 研究方法

以唯讀方式分三步：

1. **落點貫通性檢查**：對每個修改點，從「錯誤發生的位置」沿呼叫鏈往上追，
   確認例外真的能穿過中間的每一個 `except`。這是本輪的核心方法，也是上一份驗收漏掉的一步。
2. **mock 注入探針**：用 `python -I` 注入 `RuntimeError`，觀察它在哪一層被吞、下游收到什麼型別的值。
   共三個探針：`fetch_and_parse` 層、`step2_of` 層、以及模擬 v2 修改後的 cmd 層結構。
3. **測試層級比對**：拿 v2 的測試設計與 `script/support/tests/` 既有測試的 mock 層級對照，
   判斷新測試是否具備證偽能力。

<a id="gap1"></a>
### 缺口一：修改③ 落在吞噬點之外，補丁會是死代碼

這是本輪唯一會讓 v2 核心承諾失效的問題，屬阻斷級。

v2 第 37 列把 修改③ 定位在「`daily.py`（修改② 的 except 之後再加一個 except）＋`enrich_official.py` 同型位置」。
問題是這兩個位置都**收不到** `RuntimeError`。

**第一層吞噬：`fetch_and_parse`**

[`orderflow.py:210-215`](../../../script/lib/orderflow.py#L210) 的通用 except 把非 HTTPError 一律視為瞬時錯誤：

```python
        except Exception as e:  # noqa: BLE001
            print(f"  {code}: attempt {attempt + 1}/{retries} {type(e).__name__}: {e}")
            if attempt + 1 >= retries:
                return None
```

實測（注入 `RuntimeError('step_1_update failed: busy')`）：

```
  15809: attempt 1/3 RuntimeError: step_1_update failed: busy
  15809: attempt 2/3 RuntimeError: step_1_update failed: busy
  15809: attempt 3/3 RuntimeError: step_1_update failed: busy
fetch_and_parse RESULT: None CALLS: 3
```

**第二層吞噬：`step2_of`**

即使 `fetch_and_parse` 放行了，[`daily.py:95-99`](../../../script/scan/daily.py#L95) 還有一個 `except Exception`：

```python
    except Exception as err:  # noqa: BLE001
        log(f"  {rec['code']} step_2 FAIL {err}")
        rec["step2_error"] = str(err)[:150]
        rec["step2At"] = now
        return None
```

實測：

```
[23:56:52]   15809 step_2 FAIL step_1_update 失敗: busy
RESULT: None
step2_error: step_1_update 失敗: busy
--- 若 cmd 層加 except RuntimeError, 它會收到什麼？ None（不是例外）
```

**cmd 層收到 `None` 之後會怎樣**

[`daily.py:194-202`](../../../script/scan/daily.py#L194) 對 `None` 的分支是記一筆 `step2_failures` 然後 `continue`——不是 `break`、不是 raise：

```python
        d = step2_of(r, fetcher)
        if d is None:
            # step2 失敗留痕（state + alerts 可見；2026-09-08，不再靜默）
            if r.get("step2_error"):
```

**結論**：v2 的 `except RuntimeError` 永遠不會執行，`blown` 永遠是 `False`，
迴圈會把 625 碼全部掃完、每碼重試三次——正是 修改③ 要防的那件事。

**要三層都改才通**

| 層 | 位置 | 動作 | 少了它的後果 |
|---|---|---|---|
| 第一層 | [`orderflow.py:210`](../../../script/lib/orderflow.py#L210) | 通用 except 先判三關鍵字，是就 `raise`（不重試） | 例外在此被吞，下游全部收不到 |
| 第二層 | [`daily.py:95`](../../../script/scan/daily.py#L95) | `except Exception` 之前加同樣判斷，`raise` 放行 | 例外在此被吞，cmd 層收到 `None` |
| 第三層 | `daily.py` 四處 cmd 與 [`enrich_official.py:72`](../../../script/site/enrich_official.py#L72) | 接住 `RuntimeError`，設 `blown=True`、`break` | 例外穿出 `main()`，變成 exit 1 而非 exit 3 |

enrich 端只經過第一層（它呼叫 `fetch_and_parse(code)`，不經過 `step2_of`），所以對它而言是兩層：第一層放行、第三層接住。

**這個錯誤的來源是我**

我在[驗收報告的缺口一](./驗收_20261113.md)寫的是「在 cmd 層的 `except` 之後增加 `except RuntimeError`」。
當時我只驗證了「`fetch_and_parse` 會重試三次」，沒有驗證「例外能不能穿到 cmd 層」——
把「觀察到的重試現象」直接當成「修法位置」，中間少的正是本輪研究方法第 1 步的落點貫通性檢查。
v2 照單全收，把一個未經貫通驗證的建議變成了計畫的最終形態。

## 討論

### 為什麼這個錯誤能穿過兩輪檢查

第一輪（我的驗收）驗的是「現象」：注入 RuntimeError，看到重試三次、回傳 None，就判定「這是缺口」。
第二輪（v2 作者）驗的是「建議」：確認我方數字無誤，就照抄修法位置。

兩輪都沒做同一件事：**從錯誤發生的位置沿呼叫鏈往上追，確認例外在哪一層被攔下**。

這個盲點有結構性原因。`except Exception` 在 Python 裡是沉默的——
它不會回報「我攔到一個本來該往上傳的例外」，只會安靜地把控制流導向 `return None`。
閱讀程式碼時看到 `except Exception` 不會覺得異常，因為它在中斷式錯誤處理裡太常見了；
只有在跑起來、觀察下游收到什麼型別的時候，才會發現「例外不見了」。

所以這類問題的驗收方法必須是行為探針，不能是靜態閱讀。我第一輪做對了探針、但探針打錯層級：
我測的是 `fetch_and_parse`（因為那是重試發生的地方），沒測 `step2_of`（那才是例外消失的地方）。

### 三層修正的必要性

單獨改任何一層都不成立：

- 只改第一層（`fetch_and_parse` 放行）：例外繼續往上，但被第二層 `step2_of` 吞掉，cmd 層收到 `None`。
- 只改第二層（`step2_of` 放行）：例外到不了第二層，第一層已經回 `None` 了。
- 只改第三層（v2 的方案）：例外到不了第三層。

三層都改之後，控制流的完整路徑是：

```
prepare() 丟 RuntimeError
  → fetch_menu / fetch_menu_single 不攔（它們只攔 HTTPError）
  → fetch_and_parse 第一層：判三關鍵字 → raise（不重試）
  → step2_of 第二層：判三關鍵字 → raise（不記 step2_error）
  → cmd 層第三層：接住 → blown=True → break
  → save_state / update_alerts / history_row 執行
  → return 3
```

括號裡「不重試」（第一層）與「不記 step2_error」（第二層）都是必要的語意調整，不只是放行：
若第一層放行但仍重試，會變成「重試三次後才上拋」，白白多燒兩倍請求。

### 誤判面的取捨

把 `RuntimeError` 納入熔斷，代價是把「官網改版導致的 `step_1_update` 失敗」也判成熔斷。
誤擋的後果是當天少掃幾碼、次日重掃；漏判的後果是數千發重試。
兩者不對稱，v2 的取捨方向正確——但應該把這個已知誤判面寫進 v2 的「未解事項」，
