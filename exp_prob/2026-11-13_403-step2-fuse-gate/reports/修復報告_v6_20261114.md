## 前言

### 熔斷是什麼、本專案約定它該長什麼樣

官網會在請求過多時回 HTTP 429 或 403，意思是「你請求太多了，先停」。
本專案把這個信號稱為**熔斷**，約定的標準處理是：

> 收到 403/429 → 停止後續請求 → **已拿到的結果照樣存檔** → 以 exit 3 結束（區別於一般錯誤的 exit 1）→
> CI 的 commit 步驟（PR #8 加的 `!cancelled()` 條件）把存檔撿走提交 → 開告警 issue。

這條路已經在「查活」階段實作（`daily.py` 的 `probe_batch`），也在官券補全階段實作（`enrich_official.py`）——
11-12 晚間官券補全撞上 403 時就是這樣走完的：26 張已補全的資料入庫、開出 issue #9，一切按設計。
**問題在第三個使用者——「抓詳情」階段——從頭到尾沒實作這條路。**

### 三條既有 BUG

行號以 origin/main `26bbdda` 為準；完整 CI log 證據鏈見查找報告，本節為修復視角的重述。

**BUG ①：403 被誤當成「session 過期」**（`script/lib/orderflow.py:246-248`）

抓詳情階段多張券共用一個訂餐 session，`BatchFetcher` 負責管理它。修復前的代碼：

```python
try:
    html = self._session.fetch_menu(code)
except Exception:
    # session 過期/其他錯誤 → 重配一次；若仍錯往上拋（含 429/403 熔斷）
    self._roll(code)
    html = self._session.fetch_menu(code)
```

`except Exception` 不挑食：session 過期和官網 403 被一視同仁，全部去重配新 session。
但限流狀態下，重配流程（配 cookie、取門市參數、選門市的 `step_1_update`）**自己也會被擋**——
於是冒出第二個 403。這個 403 從重配流程直接往上炸，此時最初的 except 已經用掉了，
外面沒有任何人接它（下一條 BUG 就是它沒人接的原因）。
註解裡寫的「含 429/403 熔斷」只是把問題記在紙上，代碼並沒有區分。

**BUG ②：抓詳情迴圈沒人接住熔斷**（`script/scan/daily.py` 四處）

`step2_of` 的文件（daily.py:86）寫「429/403 原樣往上拋由上層呼叫端處理」，
但上層從未實作：confirm 的活券迴圈、confirm 的復活補抓、explore 的補抓、sample 的補抓——四處全是裸呼叫，沒有 try。
於是 BUG ① 冒出的裸例外一路炸穿到 `main()`，程式以 **exit 1**（一般錯誤）結束，
而不是熔斷約定的 **exit 3**。

真正的損害在這裡：`save_state`（把 627 碼查活結果寫入 `data/scan_state.json`）、
`update_alerts`、`history_row` 全部排在迴圈之後——程式死在它們之前，
**46 分鐘掃完的 627 碼結果一行都沒落地**。
11-12 兩場 CI 的 commit 步驟都只看到 `no changes`，什麼也沒撿到。

**BUG ③：熔斷日保險形同虛設**（`.github/workflows/scan.yml` gate）

`scan.yml` 的第一個 job（gate）是保險：查有沒有未關閉的失敗告警 issue，有就禁止今日掃號（防污染）。
但它有兩個洞：

1. gate job 沒有 checkout 程式碼，`gh issue list` 也沒帶 repo 參數——gh 在非 git 目錄直接報錯。
2. 指令寫成 `gh issue list … 2>/dev/null || echo 0`——gh 失敗被吞成 0，**「查詢失敗」被當成「沒有 issue」**。

兩洞合起來：熔斷日隔天，gate 根本查不到 issue，照樣放行。
實證：11-12 22:40 的備援場起跑時 #9/#10 都還開著，gate 卻輸出「gate 通過，可掃號」——
又燒了一輪 627 發、又撞了一次 403。

三條的因果關係：BUG ①＋② 是**同一事故的兩個環節**——① 把熔斷變成無人處理的裸例外，② 確保沒人處理它，
只修一處 403 還是會炸（炸點後移）；BUG ③ 是獨立的保險失效——不參與當日損害，但讓熔斷日無法止損
（22:40 的二次燒配額就是被它放行的）。

### 200 形態：忙碌頁的另一張臉

修復計畫第一版只覆蓋「HTTP 403」這一種熔斷。第三輪複審指出：11-12 的 403 打在 `fetch_menu` 的 GET 上，
**同一個位置若改回「200＋忙碌頁」，控制流裡沒有任何例外**——v1 的修改③（例外三層）全部碰不到。
官網的忙碌頁實際有兩種子形態，各有各的惡：

**子形態一：RuntimeError 形態**。忙碌頁讓 `prepare()` 的前置三步（配 cookie、取 llcs、`step_1_update`）失敗，
代碼對這三種失敗各自 raise `RuntimeError`（訊息含 `users_session_id`／`llcs`／`step_1_update` 關鍵字）。
修復前這種 RuntimeError 被當成普通瞬時錯誤重試 3 次、記 step2_error、繼續掃——每碼多燒 3 發。
修法＝**修改③三層放行**：第一層（`fetch_and_parse`）認出關鍵字就不重試直拋、第二層（`step2_of`）不記 error 直拋、
第三層（daily 四個迴圈＋enrich）接住設熔斷旗標——「查活撞熔斷」的既有出口原樣收尾。

**子形態二：垃圾成功形態（本校驗鏈最重要的發現）**。非空忙碌頁走真實解析鏈時**不會失敗**：
`parse_step2` 永不 throw、node 抽取對無資料頁正常結束、`flatten_items` 對空結構回 None——
`parse_menu_html` 回一個帶垃圾 meta 的 dict，被當成**解析成功**。實測結局：每碼 1 發、
`title`／`channels`／`desc` 被**靜默清空**、`contentChangedAt` 全洗＋假內容更動告警爆量、exit 0——
連失敗的痕跡都不留，且沒有任何例外可供攔截。文字版變體的 meta 甚至看起來完全正常（title/channels 都對），
唯一可靠的辨識特徵是**結構**（選單版頁面含內嵌 `ctidss` 結構資料且夠長，忙碌頁沒有）。

修法＝**修改⑥，兩步依賴**：

| 步 | 位置 | 動作 |
|---|---|---|
| ⑥a 有效性閘門 | `orderflow.py`：`is_menu_page`（含 ctidss 且 >180KB）改模組函式；解析分支加條件 | 非選單版**視同解析失敗**，與空回應合流——垃圾成功變成可見失敗，log 分「空回應／非選單版／變體」三形態供觀測 |
| ⑥b 連續計數熔斷 | `daily.py` 四迴圈＋`enrich_official.py` | 連續 3 碼解析失敗（`FUSE_PARSE_STREAK`，獨立常數）→ 熔斷走既有 exit 3；真成功歸零 |

⑥b 的失敗標記有兩種（`PARSE_FAIL_MARKS`）——「fetch/parse 失敗」與「疑似垃圾頁」，
後者由 **⑥a′ 上游攔截**產生：`step2_of` 收到 `items is None` 且碼不在白名單的結果時，
直接判「疑似垃圾頁」回 None——繞過頁（通過 ⑥a 門檻但 meta 無資料）的假成功到不了彙整主流程與 state 檔。
白名單三碼（`ITEMS_NONE_WHITELIST`：93015/15596/16348）是 `items=None` 的**正常無選項券**，放行。

⑥b 在五個迴圈的實際覆蓋範圍（N=3 需要連續 3 碼，各迴圈可打 step2 的碼數決定能否觸發）：

| 迴圈 | 可打 step2 的碼數 | ⑥b 有效 | 說明 |
|---|---|---|---|
| alive（confirm） | 625 | ✅ | 主要防線，分母充足 |
| dead（confirm revive） | 2（今日 16311／16312） | ❌ | 分母 < 3，同形為程式一致性保留 |
| explore（fresh） | 1,385 個潛在碼位 | ✅ | 分母充足 |
| sample（hits） | 抽樣 600 碼，歷史 91 場命中最大 1 | ❌ | 分母 < 3；M1 階段有 probe_batch 熔斷保護 |
| enrich（targets） | 47 | ✅ | 分母充足 |

白名單三碼在 `is None` 判定下的實際作用：

| 碼 | `items` 值 | 白名單作用 |
|---|---|---|
| 93015 | `[]` | 今天無作用（`[]` 本來就不被抓）——保留供日後判定改 `not items` 時使用 |
| 15596 | `None` | 有效——避免被誤判垃圾頁 |
| 16348 | `None` | 有效——同上 |

### 密度不對稱：8.6 倍（修改⑦的依據）

對 11-10 成功場與 11-12/11-13 失敗場的 CI log 逐位重算，抓詳情階段（step2）的請求密度約 **2.0 發/秒**，
查活階段（M1）約 **0.23 發/秒**——**8.6 倍**。機制：查活的每碼間隔有 `sleep_scan` 節流（每發 2s＋隨機浮動、
每 50 發中場休息），**抓詳情的四個迴圈一個都沒有**——成功路徑連續快打，11-10 是「5 分鐘快打完、總量剛好沒超標」的擦邊過。
三場失敗都在 M1 完成後 46-47 分觸發——如果把官網的限流想成一段時間內累積請求量的額度，
「M1 剛結束、額度已耗盡」的時點正是最脆弱的接縫：M1 末筆到 step2 首發只隔 2.9 秒。

修法＝**修改⑦ 節流統一**（參數經使用者拍板）：
`DEFAULT_SLEEP` 2.0→**1.0**＋U(0,2)（整體減半，M1/step2/enrich 同套）、號段等待**停用**
（`DEFAULT_SEG_GAP`＝0，常數與參數保留——兩支手動工具的命令列參數預設值引用它，刪了會炸）、
每 50 發中場休息**保留**（30s×U(0.8,1.5)，與 BatchFetcher 50 張換 session 對齊）；
四個抓詳情迴圈全部補 `sleep_scan`；**⑦c**：查活結束→抓詳情開始前插 45 秒切換休息（enrich 為獨立 job 不適用）。
效果估算：step2 密度 ~2.0→~0.33 發/秒（降 6 倍）、M1 0.23→~0.33-0.38（快 1.4 倍，策略變更）、
confirm 總長 51 分→估算 70-75 分（Phase 7 實測校正）、當日小時峰值 ~1515→~1190 發（降 20%）。
**節流能否避免 403 未經實證**——就算無效，①-⑤ 已保住成果；列 Phase 8 觀察。

### 告警的靜默失敗（修改⑧的依據）

11-13 的事故場暴露另一個次生問題：scan-failed issue 已存在時，alert 工作直接輸出「already exists, skip」——
**連續失敗零通知**。修法＝改查既有 issue 的編號，在留言補一則「再次失敗 日期：run 連結」。
完整循環見討論節的「報警系統流程與匯報通路」。

### 誤判面聲明（已知代價，明寫）

三關鍵字判定會把「官網改版導致的 step_1_update 失敗」也判成熔斷——誤擋＝當天少掃幾碼、次日重掃；
漏判＝數千發重試白燒。**不對稱，寧可誤擋**。修改⑥ 同一原則：⑥a 門檻若因官網改版漂移，正常頁被判非選單版
→ 連鎖觸發 ⑥b 熔斷——症狀明顯（全碼失敗＋exit 3＋issue），次日即知、可回滾；⑥b 對「無選項券相鄰滿 3 碼」
會誤熔斷——今日 alive 清單的連續非白名單區段為 306/312/4（零誤傷，最短段餘裕 1），
**最長連續非白名單區段 <3 時 ⑥b 失效，需告警**（列入未解事項追蹤）。

| alert 連續失敗 | 靜默 skip（零通知） | 既有 issue 補 comment＋run URL |
| session 過期／非熔斷 RuntimeError／手動取消 | 正確 | 不變 |
| 熔斷日次日／coverage | gate 誤放行、coverage 天天丟 | gate 擋、confirm commit 帶 coverage |

### 八處修改的目的分類

| 主要目的 | 修改 | 一句話說明 |
|---|---|---|
| 熔斷要接得住、成果要保得住 | ①②③⑤ | 撞到官網限流就停手、已完成的結果照樣存檔（exit 3）；隔天的保險檢查真的會擋 |
| 每天的資料不弄丟、連續失敗不再無聲 | ④⑧ | coverage 記錄隨每日 commit 入庫；連續失敗在既有告警 issue 補留言 |
| 請求要慢下來 | ⑦ | 四個抓詳情迴圈補節流，抓詳情密度從查活的 8.6 倍降到同一等級 |
| 假成功要能被認出來 | ⑥ | 忙碌頁的「假成功」變成可見失敗，連續 3 碼就熔斷 |

## 研究方法

以唯讀方式分七步定案：

1. **行為對照法**：以 CI log 的 traceback 逐幀還原缺陷鏈，再以同晚官券補全端（issue #9）的正確熔斷處理為對照組——
   修復目標不是「理想中的行為」，是「專案自己已經在別處做到的正確行為」。
2. **注入驗證法**：403 無法從外部可靠觸發，改以 mock 注入四種例外（403／429／500／連線超時）建立行為基線——
   **驗收標準在動手之前先凍結**。
3. **最小修改原則**：每處獨立、有單獨的回滾判準；不碰任何與熔斷語意無關的代碼。
4. **落點貫通性檢查**：對每個修改點，從例外產生位置沿呼叫鏈逐層追——確認沒有被中途吞掉。
5. **測試把關檢查**：mock 的位置不得移除被測邏輯——把被測邏輯 mock 掉的測試永遠全綠（假陽性；v2 版計畫曾犯）。
6. **真實鏈路探針法**：驗證「某層會怎樣」的前提時，**不得 mock 該層本身**——垃圾成功形態就是用真實解析鏈
   （真 parse＋node）才發現的；⑥a 的測試設計遵守同法：mock 只放在被測閘門的下游回傳值。
7. **量化驗算法**：節流/密度類修改先以 log 時間戳重算、對提案參數做估算表——⑦ 的參數經兩輪獨立驗算逐位一致。

工具與腳本：[`test_fuse_after_fix.py`](../test_fuse_after_fix.py)（修改①注入基線）、
[`probe_20261114_verify_v3review.py`](../probe_20261114_verify_v3review.py)（真實鏈路探針——垃圾成功形態的證據）、
review/ 兩層探針（第六輪六支＋落地審核五支，含 gate 八案例基準）。

## 討論

### 報警系統流程與匯報通路（使用者指定重申；Phase 6 反向測試後即已定稿）

這套系統的設計是「**一次故障事件＝一個 issue**」，不是「一次失敗＝一個 issue」。
第一次失敗（還沒有任何告警 issue）→ alert 工作開一個新 issue——#10 就是 11-12 那天這樣誕生的。
之後每次失敗（issue 已經開著）→ 不再開新的，改在**同一個 issue 補一則留言**——這正是修改⑧做的事；
舊代碼在這裡是靜默跳過，官網連續生氣幾天你完全無聲。疊留言在同一張單上，打開一個 issue
就能看到「失敗了幾次、每次是哪場 run」，而不是收到一疊重複的告警單。

匯報會出現在三個地方：

| 通路 | 內容 | 本次實例 |
|---|---|---|
| GitHub Actions 頁面 | run 本身是紅色（failure） | run [`43545011771`](https://github.com/happk/HutDeals/actions/runs/43545011771) 的 gate 紅叉 |
| 既有告警 issue 的留言 | 「再次失敗 日期：run 連結」（修改⑧） | #10 收到「再次失敗 2026-11-14」 |
| GitHub 通知 | issue 有新留言，repo 擁有者預設收到通知 | 同上留言推入通知 |

完整的循環（gate 的巧秒之處——**issue 的「開著狀態」同時是告警與閘門的訊號源**）：

1. 掃號失敗 → 開告警 issue（紅燈亮）
2. 隔天 gate 看到紅燈 → 拒絕掃號 → run 失敗 → alert 在 issue 補留言（燈繼續亮、計次）
3. 修好問題、確認恢復 → **關掉 issue**（熄燈）
4. 隔天 gate 看不到紅燈 → 放行，掃號恢復

也就是說：**關 issue 這個動作本身，就是告訴系統「我處理好了」**——這也是反向測試必須趁
issue 開著時做、關 issue 排在 Phase 7 的原因。實例見 Phase 6 結果節的反向測試
（run 43545011771）：gate 擋下 → alert 在 #10 補留言 → 零新告警，全鏈路按設計運作。
