## 阻斷一：⑥a 的門檻可被繞過，繞過後 ⑥b 也救不了

### 問題

v4 的 ⑥a 條件是 `parsed is None or not is_menu_page(html)`，而
[`is_menu_page`](../../../script/lib/orderflow.py#L133) 的定義是 `len(html) > 180_000 and "ctidss" in html`
——**只判長度與一個字串**。

我造了一頁 264KB、含 `ctidss` 與 `psidss`／`pprcss` 字串、但沒有任何實際資料的頁面：

```
len = 264211
is_menu_page = True
parse_menu_html items = None
  title = '系統忙碌'
  channels = []
fetch_and_parse: calls = 1 | type = dict
```

⑥a 的兩個條件（`parsed is None`、`not is_menu_page`）都不成立 → **放行**。
垃圾 meta 照樣入庫，⑥b 的計數器也不會動。

v4 自己已經寫下「`items=None` 是垃圾成功唯一可辨痕跡」（引言第 36 列、校驗第 124 列），
但沒有把它放進門檻。這是設計與發現之間的一處斷裂。

### 但不能直接把 `items is None` 當硬門檻

我查了真實 `data/scan_state.json`，**625 張活券有 3 張 `items` 為空**：

| 碼 | `items` | `channels` | 來源 |
|---|---|---|---|
| 93015 | `[]` | `[]` | 2026-09-04，無 source |
| 15596 | `None` | `['外帶']` | `daily.sample` |
| 16348 | `None` | `['外帶','外送']` | `daily.explore` |

這三張是正常券但沒有選項結構（舊記錄或該券型本來就無選項）。若把 `items is None` 當硬門檻，
它們每次掃都會被判解析失敗——不會熔斷（要連續 3 碼），但會持續產生 `step2_error` 雜訊。

### 補法

三個條件一起判，但對第三個條件用**軟判定**：

```python
# 硬失敗：解析不出東西，或明確不是選單頁
if parsed is None or not is_menu_page(html):
    → 走既有解析失敗分支（重試／計數）

# 軟訊號：看起來是選單頁，但沒有選項結構
if parsed.get("items") is None:
    → 記一筆「疑似垃圾頁」告警（不計入 ⑥b 的 streak、不重試）
```

這樣既能抓到繞過門檻的形態（264KB 那頁會留下告警），又不會誤傷那三張正常券。
若連續多碼都出現「疑似垃圾頁」，再升級為熔斷——但這是第二階段，先有告警即可。

<a id="blocker2"></a>
## 阻斷二：⑥b 的計數會被「假成功」歸零

v4 的 ⑥b 設計是「連續 N 碼解析失敗 → 熔斷」，成功分支歸零。問題是**假成功也算成功**。

我模擬 ⑥a＋⑥b 落地後的計數行為（N=3）：

```
1 全失敗           : scanned=3  blown=True
2 全垃圾成功       : scanned=10 blown=False  最終 streak=0
3 兩失敗夾一垃圾成功: scanned=12 blown=False  最終 streak=0
4 三失敗後成功     : scanned=3  blown=True
```

情境 3 是關鍵：**失敗、失敗、假成功、失敗、失敗、假成功…** 跑 12 碼仍不熔斷。
若官網回的是間歇性忙碌頁（負載平衡後端在過載時常見），這個計數器會被完全規避。

### 補法

把歸零條件從「`d` 非 None」收窄為「**真的解析出 `items`** 才歸零」：

```python
if d is not None and d.get("items") is not None:
    streak = 0          # 真成功
elif d is not None:
    # 假成功：不算失敗、也不歸零（維持 streak 或走軟告警）
    pass
```

搭配阻斷一的軟告警，假成功會在告警層面可見、同時不會洗掉計數。

## 次要三：損害數字有一處混淆

v4 第 100 列寫「抓詳情 200＋忙碌頁 … 熔斷前最多 3 碼×3 發」。但垃圾成功形態是**每碼 1 發**（我實測 `calls=1`），

同一列前半的「每碼 1 發成功」與後半的「3 發」講的是兩個不同階段（修前 vs 修後熔斷前），
建議分行陳述，否則容易被讀成矛盾。

<a id="minor4"></a>
## 次要四：`FUSE_PARSE_STREAK = FETCH_RETRIES` 的語意耦合

v4 把兩個常數綁在一起（N=3 比照重試次數），理由是「語意一致」。但它們是兩個獨立概念：
一個是**單碼重試上限**、一個是**跨碼熔斷門檻**。

日後若有人調 `FETCH_RETRIES`（例如降到 2 以省請求），熔斷門檻會跟著變鬆，這是隱性耦合。
建議 `FUSE_PARSE_STREAK = 3` 獨立定義，註解寫「與 `FETCH_RETRIES` 同值純屬當前的巧合，勿耦合」。

<a id="minor5"></a>
## 次要五：⑥a 的 log 訊息措辭

v4 要把 log 從「解析失敗（空回應/變體）」改成「解析失敗（空回應/非選單版/變體）」。
建議再區分「非選單版」與「空回應」兩種不同原因——因為 Phase 7 的真熔斷驗收要靠這行 log 辨識形態
（v4 未解事項第 184 列已列「真實忙碌頁的形態未知」）。一行訊息分不出兩種形態，驗收時會少一個觀測點。

## 建議

v4 的骨架可以動手，但要先補兩件事：

1. **⑥a 加軟門檻**（`items is None` → 疑似垃圾告警，不直接判失敗）
2. **⑥b 歸零條件收窄**（只有真解析出 `items` 才歸零）

這兩點是同一個問題的兩面：**門檻漏掉 `items` 這個唯一可靠訊號，計數器又會被假成功洗掉**。
兩者合起來，⑥ 在「間歇性忙碌頁」這種最現實的形態下會失效——而這正是 11-12 事故的形態
（連續兩場都在打完 627 碼之後才被擋，說明限流不是從第一發就開始，而是漸進的）。

其餘次要項（README、三副本、數字、常數、log 措辭）可併入同一輪修，成本很低。
