## 阻斷一：移除 `DEFAULT_SEG_GAP` 會炸掉兩支手動工具

### 問題

[修復方法 1.1](./修復方法_20261113.md) 寫：

> `pacing.py` — `DEFAULT_SLEEP = 1.0`；移除 `DEFAULT_SEG_GAP = 15.0` 與 seg_gap 邏輯（L25/L31-32）

但 `DEFAULT_SEG_GAP` 被兩處 **argparse 的 default 值**直接引用：

```python
# script/scan/scan_probe.py:41
parser.add_argument("--seg-gap", type=float, default=pacing.DEFAULT_SEG_GAP)

# script/scan/scan_run.py:116
parser.add_argument("--seg-gap", type=float, default=pacing.DEFAULT_SEG_GAP,
                    help="換號段(前2碼改變)額外隨機休息基礎(秒): ×U(0.5,1.5)")
```

而且這兩支的 `sleep_scan` 呼叫全都傳了 `seg_gap=args.seg_gap`：

| 檔案 | 呼叫位置 |
|---|---|
| [`scan_probe.py`](../../../script/scan/scan_probe.py) | 93／101／109／117／141（五處） |
| [`scan_run.py`](../../../script/scan/scan_run.py) | 168（一處） |

### 兩種移除方式的後果

| 移除什麼 | 後果 |
|---|---|
| 只移除常數 `DEFAULT_SEG_GAP` | 兩支在 **module import 時**（argparse 建構階段）就 `AttributeError: module 'script.lib.pacing' has no attribute 'DEFAULT_SEG_GAP'` |
| 只移除 `sleep_scan` 的 `seg_gap` 參數 | 六處呼叫全部 `TypeError: sleep_scan() got an unexpected keyword argument 'seg_gap'` |
| 兩者都移除 | 上述兩種錯誤同時發生 |

### 為什麼 CI 抓不到

`scan_probe.py` 與 `scan_run.py` **不在任何 workflow 裡**（v5 的邊界表自己也這樣寫）。
所以 CI 的 `pytest script/support/tests` 不會 import 它們，這兩個錯誤會潛伏到有人手動使用時才爆。

這正是第四輪次要二「字面值副本失同步」的同一類問題：**邊界表宣告「不修」的檔案，仍然會因為核心模組的改動而壞掉。**

### 補法

v5 的邊界已宣告這兩支不修，所以解法必須讓它們「不用改也能活」。三個選項：

| 方案 | 改動 | 評價 |
|---|---|---|
| A. `DEFAULT_SEG_GAP = 0.0` | 1 行 | 最小，但留下死參數且語意不明 |
| **B. 常數保留、預設改 0、docstring 註明停用** | 2 行 | **建議**——參數仍可傳，行為等於無效，CLI 完全相容 |
| C. 一併改兩支工具（移除 argparse 選項＋六處呼叫） | 約 10 行 | 最乾淨，但違反 v5 自己的邊界宣告 |

方案 B 的具體寫法：

```python
# script/lib/pacing.py
DEFAULT_SEG_GAP = 0.0   # 2026-11-14 節流統一後停用（原 15.0）；
                        # 保留常數與參數供 scan_probe/scan_run 的 CLI 相容，勿直接刪除
```

這樣 `sleep_scan` 的 `seg_gap` 參數與 L31-32 的邏輯都可以完全保留不動，
而 `seg_gap=0.0` 時 `delay += 0 * U(0.5,1.5)` 等於沒有加成——行為符合 v5 的目的。

## 阻斷二：四處迴圈都需要 `enumerate`，但只標了一處

### 問題

[修復方法 1.2](./修復方法_20261113.md) 寫：

> daily.py 四個抓詳情迴圈補 `sleep_scan(i, <codes>)`——alive（L178，`for i, code in enumerate(alive)`）、dead（L229）、explore（L320）、sample（L362）

只有 alive 那處註明了要改成 `enumerate`。實際四處的現行寫法：

| 迴圈 | 現行寫法 | 有 `i` 嗎 | 需要改 |
|---|---|---|---|
| alive | [`for code in alive:`](../../../script/scan/daily.py#L178) | ❌ | 改成 `for i, code in enumerate(alive)` |
| dead | [`for code in dead:`](../../../script/scan/daily.py#L229) | ❌ | 改成 `for i, code in enumerate(dead)` |
| explore | [`for r in fresh:`](../../../script/scan/daily.py#L323) | ❌ | 改成 `for i, r in enumerate(fresh)` |
| sample | [`for r in hits:`](../../../script/scan/daily.py#L365) | ❌ | 改成 `for i, r in enumerate(hits)` |

**四處全部都要改**，v5 只標了 alive。照著 1.2 的敘述做，其餘三處會直接 `NameError: name 'i' is not defined`。

### 第二個細節：`sleep_scan` 的第二個參數要傳什麼

`sleep_scan(index, codes)` 的 `codes` 參數有兩個用途：
1. 判斷是否為最後一碼（`if index >= len(codes) - 1: return`）
2. 判斷是否換號段（`codes[index][:2] != codes[index - 1][:2]`）

| 迴圈 | 應傳入 | 不是 |
|---|---|---|
| alive | `alive` | — |
| dead | `dead` | — |
| explore | `fresh`（篩選後的新活碼） | ❌ 不是 `codes`（那是全部潛在碼位） |
| sample | `hits`（命中的未知碼） | ❌ 不是 `codes`（那是全部隨機抽樣碼） |

v5 的 1.2 寫 `sleep_scan(i, <codes>)`，`<codes>` 這個佔位符在 explore／sample 會被誤讀成各自的 `codes` 變數——
那兩支的 `codes` 是**輸入名單**，長度與 `fresh`／`hits` 不同，傳錯會導致「最後一碼不休息」的判定失準。

### 補法

1.2 的敘述改成：

> 四處迴圈改寫成 `for i, x in enumerate(<該迴圈的名單>)`，於 `step2_of` 處理完後呼叫
> `sleep_scan(i, <同一份名單>)`——alive 用 `alive`、dead 用 `dead`、explore 用 `fresh`、sample 用 `hits`。

驗證欄加一條：「四處 diff 都含 `enumerate`，且 `sleep_scan` 的第二個參數與 enumerate 的名單是同一份」。

## 次要一：⑥a′ 白名單的長期風險在「增長」而非「相鄰」

v5 寫「未來若出現新的無選項券，會被 ⑥a′ 標記＋計數（可見），確認正常後加入白名單」——這個流程是對的。
但它對風險的描述只提到「相鄰」：

> 未來若空 items 碼在排序中相鄰，可能誤熔斷

我驗證了今日的實際位置，確認零誤傷：

| 白名單碼 | 掃描順序位置 | 前後 |
|---|---|---|
| 15596 | 0 | 無前，後 15809 |
| 16348 | 307 | 前 16347，後 16349 |
| 93015 | 620 | 前 93014，後 93022 |

而且即使全站忙碌、白名單中斷 streak，三段都仍會熔斷：

| 區段 | 碼數 | 會熔斷 |
|---|---|---|
| 索引 1-306 | 306 | ✅ |
| 索引 308-619 | 312 | ✅ |
| 索引 621-626 | 6 | ✅ |

**但反向風險 v5 沒提**：白名單碼被 ⑥a′ 排除 → 它們算「成功」→ **會把 streak 歸零**。
若白名單增長到把名單切成多段 < 3 碼的碎片，⑥b 就永遠不會熔斷。

今日三碼分散，最長區段 312 碼，安全。但這是**沒有監控的隱性前提**。

**建議**：在 v5 的未解事項加一條可量測的指標——

> 白名單碼數 / 總 alive 碼數，與「最長連續非白名單區段長度」。
> 後者 < 3 時 ⑥b 失效，需告警。

這是低成本的自保，不必現在寫程式，但要在文件裡留下判準。

## 次要二：⑧ 需要 issue number，但現行變數只有 COUNT

[修復方法 5.3](./修復方法_20261113.md) 寫：

> alert else 分支（L319-321）改為：`gh issue comment` 既有 issue——附 `RUN_URL`＋當日失敗摘要（一行）

但現行的 else 分支只有 `COUNT`：

```sh
# .github/workflows/scan.yml:313-321
COUNT=$(gh issue list --label scan-failed --state open --json number --jq 'length')
if [ "$COUNT" -eq 0 ]; then
  gh issue create --title "$TITLE" --label "scan-failed" --body "..."
else
  echo "open scan-failed issue already exists, skip"    # ← 要改成 comment
fi
```

`gh issue comment` 需要的是 **issue number**，而 `COUNT` 是用 `--jq 'length'` 算出來的數量。
照著做會拿到空字串或 0，`gh issue comment 0` 會失敗。

**補法**（把查詢改成取第一個 number）：

```sh
ISSUE=$(gh issue list --label scan-failed --state open --limit 1 \
  --json number --jq '.[0].number')
if [ -z "$ISSUE" ]; then
  gh issue create --title "$TITLE" --label "scan-failed" --body "..."
else
  gh issue comment "$ISSUE" --body "再次失敗 $DATE：$RUN_URL"
fi
```

`RUN_URL` 與 `DATE` 在 alert job 開頭已定義（[`scan.yml:274-275`](../../../.github/workflows/scan.yml#L274)），可直接用。

**建議 5.3 的敘述補上這個變數改動**，並在驗證欄加「`ISSUE` 為空時走 create、非空時走 comment 兩條路徑都檢查」。

## 節流數字驗算

v5 宣稱「M1 0.23 → 0.33 發/秒（快 43%）」。我用真實的 627 碼掃描順序模擬（200 seed 平均）：

| 情境 | 參數 | 模擬時長 | 模擬密度 |
|---|---|---|---|
| 現行 | base 2.0 ＋ U(0,2) ＋ seg_gap 15 ＋ break 30 | 39.7 分 | 0.263 發/秒 |
| v5 | base 1.0 ＋ U(0,2) ＋ 無 seg_gap ＋ break 30 | 27.8 分 | 0.376 發/秒 |

**相對倍率正確**：1.42 倍 ≈ v5 宣稱的 1.43 倍 ✅

**絕對值偏低的原因**：CI 實測 45.5 分 vs 模擬 39.7 分，差 5.8 分。
來源是重試、網路延遲、內容更動時的額外請求——這些不在 `sleep_scan` 的模型裡。

**移除 seg_gap 的貢獻有限**：627 碼只有 **6 個號段邊界**：

```
位置 2:   15809 → 16000
位置 463: 16525 → 26303
位置 615: 26999 → 92001
位置 617: 92002 → 93002
位置 622: 93022 → 94199
位置 625: 94700 → 16311
```

6 × 平均 15 秒 ≈ **1.5 分鐘**。主要加速來自 base 2.0 → 1.0（約省 10 分鐘）。

**對「confirm 總長 ~65 分」的校正**：v5 的推算假設 M1 32 分＋step2 33 分。
按 CI 實測與模擬的比例外推（實測比模擬慢約 15%），實際可能落在 **70-75 分**。
建議把 65 分標成「估算值，Phase 7 實測校正」。
