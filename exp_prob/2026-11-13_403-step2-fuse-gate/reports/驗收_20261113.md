### 缺口一：限流若以 200 錯誤頁表達，三處修改全部不觸發

這是計畫唯一會在限流日直接反噬的缺口，屬阻斷級。

重建 session 的流程在 [`prepare()`](../../../script/lib/orderflow.py#L114) 遇到 `step_1_update` 回應不含 `"success":true` 時，
丟的是 `RuntimeError`，不是 `HTTPError`：

```python
# script/lib/orderflow.py:114-115
if '"success":true' not in resp and '"success": true' not in resp:
    raise RuntimeError(f"step_1_update 失敗: {resp[:200]}")
```

而 [`fetch_and_parse`](../../../script/lib/orderflow.py#L210) 對非 HTTPError 走的是通用重試分支，
[`step2_of`](../../../script/scan/daily.py#L95) 再把它吞成 `step2_error` 回 `None`。

我的實測（mock 注入 `RuntimeError("step_1_update failed")`）：

```
  15809: attempt 1/3 RuntimeError: step_1_update failed
  15809: attempt 2/3 RuntimeError: step_1_update failed
  15809: attempt 3/3 RuntimeError: step_1_update failed
RESULT None CALLS 3
```

也就是說：**修改① session 管理器熔斷不重建的 `raise`，與修改② cmd 層接住熔斷的 `except HTTPError`，兩者都不會觸發，迴圈會繼續跑。**
每碼 3 次 `fetch`，每次 `fetch` 又各自重建一次 session、走一遍四發前置——單碼 12 發，625 碼就是數千發。

風險在於「限流」不會只有一種形態：官網完全可能以 **200 + 錯誤頁／忙碌頁**表達限流，此時沒有 HTTPError 可判。
計畫只防了 403/429 這一種表達方式，而這件事正是本次事故要防的「繼續燒配額」以另一種形態復發。

建議補一條，不改結構：在 cmd 層的 `except` 之後增加 `except RuntimeError`，
訊息含 `step_1_update` 或 `users_session_id`／`llcs` 時視為熔斷，設 `blown=True` 並 `break`。
判準放寬的理由是：這三個字串都只會在重建 session 的流程裡出現，一般解析失敗不會帶到它們。

### 缺口二：confirm 的 commit 步驟從不提交掃描覆蓋率檔

這是計畫完全沒提到、但每天都在發生的缺口，屬阻斷級。

[`cmd_confirm`](../../../script/scan/daily.py#L166) 在抓詳情迴圈之前就呼叫 `update_coverage(recs)`，檔案確實寫了。
但 [scan.yml 的 confirm commit 步驟](../../../.github/workflows/scan.yml#L84) 只收
`scan_state.json`／`scan_alerts.json`／`scan-history.md`／`public/scan_alerts.json`
——**沒有 `scan_coverage.json`**。只有 explore（[`:150-160`](../../../.github/workflows/scan.yml#L150)）與
sample（[`:224-234`](../../../.github/workflows/scan.yml#L224)）會提交它。

後果在現有資料上已可直接量測（`data/scan_coverage.json` × `data/scan_state.json`，625 張活券）：

| `last_checked` 分佈 | 張數 |
|---|---|
| 2026-09 | 527 |
| 2026-10 | 59 |
| 2026-11 | 29 |
| 無記錄 | 10 |

**527 張（84%）的覆蓋率停在 9 月。** 原因是閉環：explore 依設計跳過 confirm 已確認的 alive/dead
（[`daily.py:304-308`](../../../script/scan/daily.py#L304)），sample 只掃未知號段，
於是那 625 格的更新只寫在 confirm 的 workspace 裡，每天被丟掉。

對修復計畫的意義：熔斷日 confirm 會 `exit 3` → `needs: confirm` 的 explore 與 sample 全 skip
→ **那天 `scan_coverage.json` 的 627 筆更新仍然全部丟失**。state 保住了、alerts 保住了、history 保住了，
但「失敗也入庫」只做到四分之三。計畫完全沒有提到這份檔。

建議新增一處修改，兩行：把 `data/scan_coverage.json` 加進 confirm commit 步驟的 diff 檢查與 `git add`。
這同時解掉「84% 停在 9 月」這個既有資料品質問題。

<a id="gap3"></a>
### 缺口三：gate 反向測試會測到舊版 workflow

[修復方法第 53 列](修復方法_20261113.md) 要求「#9/#10 還開著時 dispatch 一場」。但情況是：

- `git ls-remote --heads origin fix/step2-fuse-gate` → **空**，該分支不存在於遠端。
- `git rev-parse --abbrev-ref @{u}` → `origin/main`；`git rev-list --count origin/main..HEAD` → **1**，尚未 push。
- GitHub 的 `schedule` 事件永遠只使用預設分支的 workflow 檔。

若照目前排序（Phase 3 驗收 → Phase 4.2 才 push），反向測試的 dispatch 只會跑到 main 上的**舊版 gate**，
結果是「照樣放行」，而這會**看起來像修復失敗**——實際上只是測到舊碼。

建議把順序改成：修改③ gate 改 fail-closed 改檔 → YAML 靜態檢查 → **先 push 分支** → 以 `--ref fix/step2-fuse-gate` dispatch
→ Phase 4 再走 PR 或合併。並在步驟表註明「`--ref` 不可省」。

<a id="gap4"></a>
### 缺口四：gate 修法對空字串仍放行

屬補強級，不阻塞執行。

移除 `|| echo 0` 後，`set -e` 確實會在 gh 失敗時中止 step——我以 Git Bash 驗證：

```
$ set -e; X=$(false); echo "SHOULD_NOT_PRINT"
（無輸出，立即結束，exit 1）
```

但 gh 成功而 jq 產出空字串時（或 `RUNNING` 為空），比較式在 `if` 條件內不會觸發 `set -e`：

```
$ bash -c 'set -e; OPEN=""; if [ "$OPEN" -gt 0 ]; then echo BLOCKED; fi; echo PASSED'
[: : integer expression expected
PASSED
```

條件判假 → 落到 else → `should_run=true` → **放行**。機率低（`--jq length` 正常會印 `0`），
但既然修法的立意是「查不到＝擋」，建議補一段整數驗證：

```sh
case "$OPEN" in ''|*[!0-9]*) echo "gate 查詢結果異常($OPEN)，保守擋下"; exit 1;; esac
```

`OPEN2` 與 `RUNNING` 同形。

<a id="gap5"></a>
### 缺口五：注入測試只涵蓋 session 管理器，未涵蓋 cmd 層

屬補強級。

[修復報告](修復報告_20261113.md) 的驗收清單寫「注入測試四條全綠＝修改① session 管理器熔斷不重建成立且無回歸」。
但 [test_fuse_after_fix.py](../test_fuse_after_fix.py) 只建構 `BatchFetcher` 與 `FakeSession`，
測的是 [`BatchFetcher.fetch`](../../../script/lib/orderflow.py#L240) 的 except 分支
——**cmd 層四處（修改② cmd 層接住熔斷）完全沒有測試**，而「四條全綠」在修完修改①之後就會成立。

也就是說：目前的驗收清單會讓「修改① 綠燈」冒充「修改① 與修改② 都綠」。
計畫的 Phase 2.2 確實寫了要新增 cmd 層注入測試，但驗收敘述與 2.2 對不上。

建議在驗收清單明寫「第一條＝修改① session 管理器熔斷不重建專屬；第二條＝修改② cmd 層接住熔斷專屬」，並補上
`step2_of` 拋 403 時 `cmd_confirm` 是否 `break` 並 `return 3` 的測試——可直接 mock
[`daily.step2_of`](../../../script/scan/daily.py#L80)，不需真網路。

另外，計畫的「修復範圍邊界」表未提兩處同型裸呼叫：
[`scan_probe.py:122`](../../../script/scan/scan_probe.py#L122) 與 [`scan_run.py:69`](../../../script/scan/scan_run.py#L69)。
它們同樣是 `fetch_and_parse` 的無接手呼叫。經查不在任何 workflow 內，屬手動工具，不修可以接受，
但應在邊界表明寫「刻意不修」，否則下一個讀者會以為是漏修。

## 討論

### 主線為什麼可信

三份文件最有力的一點，是它把「損害」拆成了「觸發／誤判／缺口」三層，並且每一層都指向不同的程式位置。
這種拆法可以證偽，而它也確實被證偽通過了：traceback 的每一幀都能對上原始碼，`no changes` 的 log 也存在。
更關鍵的是它找到了**同晚的同類事件作為對照組**——官券補全端同樣吃 403、同樣是熔斷，
卻在 [`enrich_official.py:55-63`](../../../script/site/enrich_official.py#L55) 完整走完「停止 → 入庫 → exit 3 → 開 issue」。
用「專案自己已經在別處做到的正確行為」當修復目標，比任何理想化設計都可靠，也讓修復範圍自然收斂。

範圍邊界同樣劃得對：不重構 session 管理、不改 `step2_of` 的回傳語意、不處理 runner 飢餓。三件事都有明確理由，
不是「來不及所以不做」。這一點在後續 review 時會省很多爭論。

### 缺口一為什麼值得優先處理

修復計畫的核心承諾是「撞到限流就停手，不繼續燒配額」。但這個承諾建立在一個假設上：限流一定以 403/429 表達。
一旦官網改用「200 + 錯誤頁」——這在實務上很常見，尤其台灣的電商後端常以 `{"success":false}` 或空殼頁回應過載——
整個防線會靜默失效：既不熔斷、也不報錯，只是把每一碼重試三次。這種失效形態比本次事故更糟，
因為它不會留下 traceback，只會在 log 裡留下一行行 `attempt 1/3`，而那些行本來就會被歸類為「瞬時錯誤」。

建議的補法成本極低（一個 `except RuntimeError` 分支），但它把「熔斷」從「HTTP 狀態碼的判讀」升級為
「呼叫流程的判讀」——後者才是官網真正在表達的意思。

### 缺口二其實比缺口一更常發生

缺口一需要官網改變限流的表達方式才會出險，機率未知。
缺口二則是**每天都在發生**：527 張活券的覆蓋率停在 9 月，這件事與 403 無關，是 confirm 的 commit 步驟漏了一個檔。
它只是因為這次熔斷才被「失敗也入庫」的討論照到。

換句話說：如果只修計畫列的三處，事故重演時 state 會保住、coverage 會丟；而平常日子裡 coverage 也一直在丟。
把這 2 行加進 confirm commit 步驟，是本次修復裡性價比最高的改動。

### 對最小修改原則的評價

文件用「歷史教訓（`9f44bb9-1` 的條件放寬造成二次事故）」來論證收窄，這個理由站得住。
但「最小」不等於「只改被點名的三處」——[缺口一](#gap1)與[缺口二](#gap2)都是同一條控制流上的鄰居，
不補的話「最小修改」會變成「最小但不完整」。建議在修復報告的範圍表裡，把這兩處從「不修」改成「併入」，
並在邊界表裡明寫 `scan_probe.py` 與 `scan_run.py` 是「刻意不修，因不在任何 workflow」。

### 建議的執行順序

1. 修改① session 管理器熔斷不重建 → 注入測試 403/429 轉綠、500/timeout 維持綠。
2. 修改② cmd 層接住熔斷，四處同形 ＋ **cmd 層專屬注入測試**（mock `daily.step2_of` 拋 403）→ 斷言 `blown` 與 `return 3`。
3. 補[缺口一](#gap1)（`except RuntimeError` 兜底判熔斷）。
4. 補[缺口二](#gap2)（confirm commit 加入 `scan_coverage.json`）。
5. 修改③ gate 改 fail-closed ＋[缺口四](#gap4)（整數驗證）。
6. **push 分支** → 反向測試（`--ref` 指定）→ 解[缺口三](#gap3)。
7. 關 issue、`smoke=true` 驗收、次日觀察。

  若要實證，只能等下一次限流，或從歷史 log 裡找 `step_1_update 失敗` 卻沒有 403 的案例（目前未找到）。
