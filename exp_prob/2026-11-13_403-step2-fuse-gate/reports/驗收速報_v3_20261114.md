## 阻斷一：最可能的 200＋錯誤頁形態完全沒堵

### 問題

③a 判定的是 `RuntimeError` 的訊息關鍵字，而 `RuntimeError` **只可能來自 [`prepare()`](../../../script/lib/orderflow.py#L87)**
的三個點：[`:92`](../../../script/lib/orderflow.py#L92)（未配發 session）、[`:99`](../../../script/lib/orderflow.py#L99)（無 llcs）、
[`:115`](../../../script/lib/orderflow.py#L115)（`step_1_update` 失敗）。

但事故當天的 403 打在 [`fetch_menu` 的 GET:124](../../../script/lib/orderflow.py#L124)——**不是 `prepare`**。
同一個位置若改成「200 ＋ 忙碌頁」，控制流是：

```
fetch_menu 正常返回 HTML（無例外）
  → parse_menu_html 回 None
  → fetch_and_parse 的解析失敗分支（orderflow.py:217-222）：重試、退避、continue
  → 三次後 return None
  → step2_of 記 step2_error、return None
  → cmd 層 continue
```

全程沒有任何例外，③a／③b／③c 都不會觸發。

### 實測

`parse_menu_html` 回 `None`、fake fetcher 回忙碌頁：

```
  15809: attempt 1/3 解析失敗（空回應/變體），重試
  15809: attempt 2/3 解析失敗（空回應/變體），重試
  15809: attempt 3/3 解析失敗（空回應/變體），重試
fetch_and_parse 回傳=None | fetch 被呼叫=3 次
```

### 損害規模

| 管線 | 請求量 | 最終結果 |
|---|---|---|
| 掃號 confirm | 625 碼 × 3 次 = **1875 發** | `step2_of` 記 625 筆 `step2_error`，`cmd_confirm` 回 **0**（不是 3） |
| enrich | `fetcher=None` 走 [`fetch_menu_single`](../../../script/lib/orderflow.py#L138)，每次重試新建 session（4 發）→ 每碼 12 發 | 47 碼 = **564 發**，同樣不熔斷 |

這也是為什麼 v3 對照表第 96 列「第一層即停（每碼 1-3 發）」與第 97 列「141-423 發」
對這一形態都不成立——它們描述的是 `RuntimeError` 形態，不是解析失敗形態。

### 補法

③a 之外還需要「**無例外的解析失敗**」的熔斷。最小做法是在
[`orderflow.py:217-222`](../../../script/lib/orderflow.py#L217) 的解析失敗分支加一條判定：
**同一碼連續 `retries` 次解析失敗**即視為熔斷，不再回 `None`，改為拋一個可辨識的例外或回哨兵值。

判定依據要能區分「單碼頁面變體」與「整站回忙碌頁」——最簡單且穩定的做法是
**連續 N 碼都解析失敗**才熔斷（單碼變體不會連續發生）。這個 N 可以取 3，
比照 `FETCH_RETRIES`，語意一致。

<a id="blocker2"></a>
## 阻斷二：測試層級仍然繞過 ③a

v3 把測試從 mock `daily.step2_of` 改成 mock `daily.fetch_and_parse`，方向對、但只救了 ③b。

原因是 [`daily.py:26`](../../../script/scan/daily.py#L26) 是 `from script.lib.orderflow import BatchFetcher, fetch_and_parse`
——mock `daily.fetch_and_parse` 只換掉 daily 模組內的綁定，`orderflow.fetch_and_parse`（③a 的所在）根本不會被執行。

實測：

```
daily.fetch_and_parse is orderflow.fetch_and_parse -> True
mock daily 之後 orderflow 仍是原函式 -> script.lib.orderflow fetch_and_parse | ③a 完全未被呼叫
```

也就是說：**在「③a 完全沒實作」的世界裡，v3 的三個案例依然全綠。** 我以模擬實作驗證過，`blown` 照樣是 `True`。

### 補法

加第 4 個案例，層級下移到 orderflow，沿用 [`test_fetch_retry.py:56-61`](../../../script/support/tests/test_fetch_retry.py#L56) 的既有寫法：

```python
fetcher = _Flaky(99, RuntimeError("step_1_update 失敗: busy"))
with self.assertRaises(RuntimeError):
    fetch_and_parse("91113", fetcher, sleep=lambda _: None)
self.assertEqual(fetcher.calls, 1)      # 不重試
```

這個案例同時守住「不重試」這個語意——沒有它，③a 寫成「重試三次後才上拋」也會綠燈。

### 一、confirm 的 dead 迴圈在 alive 迴圈熔斷後仍會打 step2

③c 的 `break` 只跳出當時所在的迴圈。[`cmd_confirm`](../../../script/scan/daily.py#L229) 的 `for code in dead` 在 alive 迴圈之後，
alive 迴圈熔斷 `break` 後，dead 迴圈照跑，復活碼仍會呼叫 `step2_of`——熔斷後又燒 1-3 發。

以記憶體內補丁（未寫檔）實測 ③c 的 break 行為：

```
step2 call order: ['A1', 'D1']
return code: 3 (3 = fuse)
after alive-loop fuse, dead loop still called step2? True
```

**補法**（3 行）：進 dead 迴圈前判 `if blown: `，跳過 step2 補抓，但死亡/復活判定照做——不影響資料正確性。

## 建議

v3 的骨架可以動手，但要先補兩件事，否則核心承諾仍然只兌現一半：

1. **③a 擴及「無例外的解析失敗」**——這是 200＋忙碌頁最可能的形態，也是 11-12 那個 403 的同一個端點。
2. **第 4 個測試案例下移到 orderflow 層**——否則 ③a 無效時測試仍會綠。
3. dead 迴圈在熔斷後跳過 step2（3 行）。
4. 更新 commit 清單、補上 `test_step2_visibility` 的守門員說明。

第 1 點不是「修 v3 現有條目」，而是新增覆蓋面：v3 把 修改③ 定義成「`RuntimeError` 語意」，
那就只覆蓋了一半的 200 形態。要嘛把 修改③ 的定義擴寬（改稱「非 HTTP 形態的熔斷」），
要嘛另立 修改⑥。前者語意更完整，後者 diff 更獨立——這個取捨留給計畫作者。
