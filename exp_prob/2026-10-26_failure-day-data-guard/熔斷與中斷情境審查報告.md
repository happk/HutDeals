# 熔斷與中斷情境審查 — 分析報告（2026-10-26）

> 目標：為掃尾三項修復（見[修復計畫報告](掃尾三項修復計畫報告.md)）做情境級審查——逐場景核對 workflow 各 step 條件的行為，找 v1 修復的缺口。
> 基準：v1 修復（四個 commit step 加 `if: !cancelled()`）＋ v2 補強（三個發布/sitemap step 同條件）；代碼基準 main `06737eb`＋本分支變更。
> 方法：GitHub Actions 條件語意逐條核對（`failure()`／`success()`／`cancelled()` 的真值表）、step 順序與依賴走查、`yaml.safe_load` 結構 dump 逐項目視。
> 產物：[probe_wf_yaml.py](probe_wf_yaml.py)（workflow 結構斷言，可重跑）。

## 結論

v1 修復抓到 v0 的問題（熔斷日資料丟 runner、alerts 停昨日），但 v1 自身有一個缺口：**發布產物不一致**——熔斷日 commit 的資料檔是新的、發布產物（`public/scan_alerts.json`、`sitemap.xml`）卻因為對應 step 被 skip 而是舊的。v2 補強＝三個純本地重生成 step（sample 的 Publish alerts、update 的 Generate sitemap／Publish alerts）與 commit step 同條件 `!cancelled()`。其餘九個設想情境（含手動取消落點三變體、gate skip、build 失敗、rebase autostash 交互）核對後無新問題。

## GitHub Actions 條件語意（本審查的根據）

| 條件 | 成功 | 失敗 | 取消 | 說明 |
|---|---|---|---|---|
| `failure()` | ✗ | ✓ | ✗ | 取消≠失敗——**手動取消本來就不開紅 issue**（alert job 行為，未動） |
| `success()` | ✓ | ✗ | ✗ | dispatch step 用它；全 skip 時成立（gate 讓賢日 dispatch update 無害，既有行為） |
| `always()` | ✓ | ✓ | **✓** | 連取消都執行——**這是 todo 原修法不能用它的原因**（截斷檔上 main 風險） |
| `!cancelled()` | ✓ | ✓ | ✗ | **失敗要撿、取消不撿**——本次修復採用 |

### 手動中斷的完整答案（修復後，回應使用者問題）

取消一個 run 的瞬間：進行中的 Python 被 kill（可能留下半寫檔）→ 該 job 的 commit step 因 `!cancelled()` **不執行** → 半成品留在 runner 銷毀 → main 與網站維持前一筆完整狀態 → 紅 issue **不開**（failure() 不成立）→ admin 警報停在上一次成功 commit 的版本 → 下次重跑從乾淨 main 開始，無需清理。唯一例外：取消落在 commit step 自身的 push 循環中段——push 是原子的，main 只會收到完整 commit。

## 驗證方法的可靠性邊界

「可靠」是對範圍說的——驗證只為它覆蓋的東西提供證據，對覆蓋之外的空間不是「不可靠」而是**沉默**。本批修復針對的 bug 全部住在沉默的空間裡。（實際執行的驗證動作盤點見[修復計畫報告](掃尾三項修復計畫報告.md)「驗證動作盤點」節。）

| 驗證層 | 性質 | 可靠的範圍 | 天生盲區 |
|---|---|---|---|
| 單元測試（合成輸入） | 決定性、可重複、隔離 | Python 邏輯照設計運作 | 不驗設計對錯、不驗系統整合 |
| 結構快照（probe） | 對檔案文字做斷言 | YAML **有**正確的條件字串 | 有條件字串 ≠ runner 真的照它運作 |
| 情境走查（本報告主體） | 推理 | 設計自洽、條件語意組合無矛盾 | 推理有錯誤率——本 session 實錄：cb13be8-1 曾被過度推斷為「dead→empty 通道整死」，後被 48 筆 empty 的資料糾正（卡死僅 15 筆缺欄位遺留） |

**為什麼測試全綠、bug 卻一直存在**：

1. **bug 是 code reading 找到的，不是測試找到的。** 「熔斷日已寫檔的資料會怎樣」這個問題在既有測試套件裡沒有對應測試存在。全綠的語意＝「被覆蓋的空間裡沒有已知 bug」，不是「沒有 bug」。
2. **失敗日是稀有事件，且症狀被文案掩蓋。** 就算熔斷發生過——資料默默丟在 runner 銷毀——alert issue 文案寫「已完成部分已由各 job 自行 commit」，把遺失現場描述成一切正常。靠「觀察線上異常」這種驗證也抓不到。這是 9f44bb9 三條能在 repo 安靜躺六週（2026-09-08 記錄）的原因。

**本 session 的兩個方法論實證**：

- **v1→v2 補強**：單元測試與結構 probe 全綠的狀態下，是紙面走查發現了「新資料檔配舊發布產物」的不一致——任何單一層都不夠，層間互補才可靠。
- **load_state patch 陷阱**：測試自身第一版有 bug（patch 錯位置、讀到真實 state），但測試大聲失敗暴露它。驗證的可靠依賴的是「錯的測試會炸出來」，不是「測試不會錯」。

**第四層（runner 真實求值）merge 前無法覆蓋**：smoke＋Cancel 不是對分層驗證的不信任——它是唯一能覆蓋 GitHub 條件求值器的測試，該求值器不在本機。分層驗證曾有一次完整預測被現實檢驗：PR #7 搜尋修復（本地 54 測試＋probe 綠 → 部署後線上命中 363/342/1 與測試集期望完全一致）。本批的差別只在最後一層 merge 前蓋不到——所以明寫為「已知未驗證」＋給可執行的覆蓋計畫（smoke＋Cancel），而非假裝綠燈等於驗完。
